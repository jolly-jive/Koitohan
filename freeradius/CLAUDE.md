# CLAUDE.md(`freeradius/`)

リポジトリの直下の `CLAUDE.md` の続きで、`freeradius/` に関わる部分。全体の構成、コマンド、複数のディレクトリにまたがる注意は直下にある。

**FreeRADIUS。** イメージは `freeradius/build/` から `koitohan/freeradius` をビルドする。元は `cayenneryo/freeradius-server`(v4 の開発ブランチを `jolly-jive/freeradius-server-image` でビルドしたもの)で、タグは Dockerfile の `FROM` で固定している。足しているのは nftables のパッケージと、送信元を制限する `entrypoint.sh` だけで、ルールを入れたあと元の `/docker-entrypoint.sh` に渡す(`ENTRYPOINT` を置き換えると元の `CMD` が消えるので、`CMD` も書き直している)。元のイメージを更新するときは `FROM` のタグを変え、`make test` で確かめる。元のイメージ標準の `/etc/freeradius` をそのまま使い、Koitohan として書いたものだけを `freeradius/config/` に置いて `:ro` で重ねる。追加ファイル(`dictionary.d/`、`mods-available/ldap_openldap`、`mods-available/detail.log`、`policy.d/authz_vendor_role`、`sites-available/ldap-pap`、`clients.conf`)は個別にマウントし、`mods-enabled/` と `sites-enabled/` はディレクトリごと置き換える。この2つの中身はシンボリックリンクで、`../mods-available/xxx` はコンテナ内でイメージ側のファイルに解決される(ホスト上ではリンク切れに見えるのが正常)。イメージ標準のモジュールを有効・無効にするときは、このリンクを増減する。

設定ファイルは3種類に分かれる。
- 共通(追跡する): `Koitohan.dict`、`authz_vendor_role`、`ldap-pap`、`detail.log`(イメージの同名のファイルを置き換える。直下の `CLAUDE.md` の「ログローテーション」を参照)、`mods-enabled/`・`sites-enabled/` のリンク。
- 利用者が環境に合わせて書く: `clients.conf`(ignore)。`clients.conf.sample` を追跡する。
- `.env` から生成: `mods-available/ldap_openldap`(ignore)。`scripts/generate_freeradius_ldap.sh` が書き出すので、直接編集しない。

認証の流れ: 仮想サーバー `ldap-pap` が LDAP バインドで認証し、`memberOf` を `control.LDAP-Group` に取り込む。`authz_vendor_role` は、ロールのないユーザーをバインドの前に拒否する(理由は応答に付けず、`%log.warn` で出す。これは `radiusd -X` のときしか見えない)。続いて `clients.conf` の `nas_type` を `Koitohan-Reply-Type`(`Koitohan.dict` で定義)に正規化し、ロール(`admin` / `operator` / `readonly`)との組み合わせでベンダー固有の応答属性を返す。複数のロールに所属するユーザーは、いちばん弱いロール(`readonly`、`operator`、`admin` の順)として扱う。権限に関わるので弱い側に倒す、というユーザーの決定で、`memberOf` の並び順に頼る形に戻さないこと。`ldap_openldap` の `control.LDAP-Group += 'memberOf'` も `:=` に戻さないこと(最初の値しか残らず、ポリシーにほかのロールが見えなくなる)。ポリシーのローカル変数への代入は `:=` で書く(v4 の `=` は「まだなければ設定」で、ループの2回目以降が効かない)。OpenSSH の `koitohan-update-users` も同じ順で、入れるグループを1つに決める。順序を変えるときは、この2か所とスモークテストを揃える。`authz_vendor_role` では、順序をロールごとの数値(弱いほど大きい)で表し、同じ数値をあとの `switch` の `case` にも書いている(unlang に定数がなく、`case` に変数を書けないため)ので、両方を直す。`koitohan-update-users` は `update-users.sh` の `weakest()` の並び。スモークテストは、`smoke01` にロールを足す順序が新しい順序でも「最初の値」と「いちばん強いロール」の両方と食い違うように組み直す。文書は `docs/configuration.md` と `docs/configuration.ja.md` の「ユーザーとロール」、`docs/basic-design.md` の 5.3 節と 7.2 節(例も含めて)に順序が書いてある。3つのロール以外のグループは何の権限も与えず、それにしか所属していないユーザーは、ロールのないユーザーと同じく、`nas_type` を見る前に拒否する(以前は `Management-Privilege-Level = 1` で許可していたが、機器種別を見ないので `readonly` より強くなる場合があり、ユーザーの決定でやめた)。`ldap_openldap` の `pool` と `bind_pool` には `backlog_on_failed_conn = yes` を書いている。FreeRADIUS は、OpenLDAP が閉じた接続に、次に使うときまで気づかない。この設定があると、気づいた要求を、張り直した接続で送り直す。既定(なし)では、その要求を失敗にして拒否を返す(OpenLDAP の再起動のあとの最初の2回のログインと、OpenLDAP が止まっているあいだのすべてのログイン)。外さないこと。OpenLDAP が止まっているあいだは、応答しない(30 秒待って要求を捨てる)のが意図した動作で、機器は応答がないときだけ、ほかの RADIUS サーバやローカル認証に回る(拒否は確定の答えとして扱う)。冗長構成でも同じ設定が合うので、切り替えの変数にはしていない(ユーザーと相談して決めた。FreeRADIUS が両方の台の OpenLDAP を使う形にするときは見直す。設計書の 5.8 節と 12 節)。上流の不具合ではなく、設定の項目(上流の 7ac2c14)なので、報告はしていない。新しいベンダーを足すときは、辞書の enum、`nas_type` の正規表現、各ロールの `case`、スモークテスト(`tests/clients.conf` と `tests/smoke.sh` の期待値)、文書の表(`docs/configuration.md` と `docs/configuration.ja.md` の「RADIUS クライアント」の `nas_type` の表と、`docs/basic-design.md` の 5.3 節の表)の5か所を揃える。
