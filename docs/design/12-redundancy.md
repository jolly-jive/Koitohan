# Koitohan 基本設計書

[基本設計書（概要と目次）](../basic-design.md)の一部。「N 節」という参照は、目次から章のファイルをたどる。

## 12. 冗長構成

検討中である。Koitohan を2台で動かし、片方が止まっても、機器の認証とログの収集が続くようにする。

- 機器は、2台の両方を RADIUS、syslog、NTP のサーバとして設定する。ログは両方に届くので、台のあいだで同期しない（8 節の「バックアップと復元」）。
- 台のあいだで同期が要るのは、LDAP ディレクトリ（ユーザ、ロール、パスワード、ロック）である。OpenLDAP のマルチプロバイダー（12.1 節）で同期する。
- TFTP の `configs/` は同期しない。機器がどちらの台に送るかは、機器の設定で決まる。
- 利用者作業用コンテナは、台ごとに `OPENSSH_HOSTNAME` を変える（7.9 節）。ユーザとロールは、各台のコンテナが LDAP ディレクトリから定期的に読み直して揃える（7.2 節）。

### 12.1 OpenLDAP のマルチプロバイダー

2台の OpenLDAP が、互いに相手を複製元とする（`syncprov` オーバーレイと、相手を向いた `syncrepl`。delta-syncrepl）。どちらの台でも書き込みを受け付ける。

**方式の選択**

LDAP ディレクトリへの書き込みは、どちらの台でも起きる。

| 書き込み                                         | 起きる台                                  |
| ------------------------------------------------ | ----------------------------------------- |
| ユーザの管理（4.7 節）                           | こいとはん管理者が作業した台              |
| `passwd`（7.5 節）                               | ユーザがログインした台                    |
| 認証の失敗の記録とロック（4.8 節）               | 機器が RADIUS を送った台。失敗のたびに書く |
| サービスアカウントのパスワードの変更（4.10 節） | その台                                    |

片方を読み取り専用の複製先にすると、複製先で起きた書き込みを複製元へ回す仕組み（chain オーバーレイなど）が要り、手間はマルチプロバイダーと変わらない。そのため、マルチプロバイダーを採る（2026-11-05 に決定）。

複製は delta-syncrepl で行う（2026-11-05 に決定）。通常の syncrepl は、同じエントリへのほぼ同時の書き込みで、片方を黙って失う。

- 通常の syncrepl は、変更のあったエントリをまるごと送り、受け取った側は、新しい `entryCSN` を持つほうで上書きする。
- delta-syncrepl は、変更の差分（accesslog オーバーレイ）から変更の操作を送り、属性の単位で合わせる。代わりに、差分のためのデータベースが台ごとに1つ増える（「変更の差分（accesslog）」の項）。

当初は、LDAP ディレクトリが小さいので通常の syncrepl で足りると考えていた。試作で、次のことを確かめて改めた。試作は、2つの OpenLDAP（Alpine 3.24 の 2.6.15）を1台の Docker ホストで動かし、ppolicy を Koitohan と同じ設定（10 回の失敗で 300 秒のロック）にした。TLS は使わず、複製は rootdn で bind させた。

| 確認                                                   | 通常の syncrepl                                  | delta-syncrepl                      |
| ------------------------------------------------------ | ------------------------------------------------ | ----------------------------------- |
| 2台で交互に、1 秒おきに失敗 10 回                      | 両方で 10 回、ロック                             | 同じ                                |
| 2台で同時に 20 回ずつ失敗                              | 20〜21 回しか残らない                            | 40 回                               |
| 2台で同時に 6 回ずつ失敗                               | 6 回しか残らず、ロックされない（2 回中 2 回）    | 11〜12 回で、ロック（9 回中 8 回）  |
| 片方でパスワードを変える最中に、もう片方で失敗を記録   | 5 回中 3 回、変更が消えて古いパスワードに戻る    | 5 回中 5 回、新しいパスワード       |
| 片方でロックを解除する、成功で失敗の記録が消える       | 相手の台にも届く                                 | 同じ                                |
| 片方を止めているあいだの失敗                           | 戻ったあとに合算される                           | 同じ                                |

認証の失敗はどちらの台でも起きるので、`passwd` の直後に、他方の台で誰かが認証に失敗するだけで、パスワードの変更が消えうる。通常の syncrepl では、これを避けられない。

**パスワードポリシーのロック**

- 失敗の記録（`pwdFailureTime`）は、2台の分が合算される。片方の台でかかったロックと、その解除（4.7 節）は、相手の台にも届く。
- 2台でほぼ同時に失敗が重なると、ロックが遅れることがある。試作では、合計で 12 回の失敗が記録されたのに、ロックされなかったことが一度あった（9 回中 1 回。再現はしていない）。各台がロックを決めるのは、失敗の時点で自分の台にある記録の数を見たときで、相手の台の失敗がまだ届いていなければ数に入らないため、と見ている（未確認）。この見立てのとおりなら、次の失敗でロックされ、遅れは最大で「台の数 ×（上限 − 1）」回にとどまる。
- ppolicy の説明書（`slapo-ppolicy`）は、複製のときの運用属性の振る舞いを「仕様が定まっておらず、保証しない」としている。OpenLDAP を更新するときは、スモークテストでこの節の動作を確かめる。

**複製するもの**

- 複製するのは、データのデータベース（`{1}mdb`）だけとする。
- `cn=config` は台ごとに持つ。`olcServerID`、管理者のパスワード（4.11 節）、TLS の設定は台ごとに違い、起動スクリプトが起動のたびに書く。複製すると、互いに書き戻し合う。
- 変更の差分（accesslog）は、台ごとの別のデータベース（`{2}mdb`）に置く。データのデータベースを `{1}mdb` のままにして、それを名前で指す LDIF（4.6 節、4.8 節）と稼働中の環境を変えずに済むようにする。試作で、この並びでも同じ結果になることを確かめた。

**サービスアカウント**

台ごとに別のアカウントにする（2026-11-05 に決定）。名前は `.env` の `FREERADIUS_SERVICE_ACCOUNT_NAME` と `OPENSSH_SERVICE_ACCOUNT_NAME` で台ごとに変える。

- エントリは複製されるが、パスワードは各台の `secrets/` にある（4.10 節）。共有すると、パスワードを変えるたびに、相手の台のファイルも差し替えることになる。分ければ、各台は自分のアカウントだけを変えればよい。
- 初期投入（4.6 節）の LDIF には、自分の台のアカウントしか入らない。相手の台のアカウントは、複製で届く。

**複製の身元**

相手の台の `syncrepl` は、パスワードのアカウントではなく、クライアント証明書で bind する（SASL EXTERNAL。2026-11-21 に決定）。

- 要る権限は、データのツリー全体（`userPassword` と、ppolicy の記録を含む運用属性を含む）と変更の差分（`cn=accesslog`）の読み取りである。書き込みは要らない。受け取った側は、自分のデータベースに自分で書く。
- パスワードのアカウントにすると、2台目が最初に bind するための身元が、1台目に先に要る。2台目は空から始めるので（「2台目の始め方」）、2台目のパスワード（またはそのハッシュ）を、1台目へ帯域外の方法で運ぶことになる。CA の証明書（公開してよいもの）と違い、秘密を運ぶ手順が1つ増える。証明書なら、運ぶのは、どちらにしても要る CA の証明書だけである。パスワードがないので、ppolicy のロックで複製が止まることも、パスワードの変更（4.10 節）も、`secrets/` のファイルもない。
- 各台の CA は、複製用のクライアント証明書を1枚発行する（「証明書」の項）。受ける側は、その subject を、決まった DN（試作では `cn=replication,cn=koitohan`）に対応づける（`olcAuthzRegexp`）。この DN のエントリは置かず、パスワードもない。データと `cn=accesslog` のアクセス制御に、この DN を書く。相手の台の名前を設定に書かずに済む。
- 検索の件数の上限（フロントエンドの `olcSizeLimit`）は外す（`unlimited`。2026-11-21 に決定）。いまは 500 で、初期投入で作る `cn=config` に書いてある（`openldap/build/entrypoint.sh`）。OpenLDAP の既定と同じ値で、イメージを Alpine に移したときに書き出したものである。
  - 上限があると、複製は黙って壊れる。試作で、2台目は 500 件で止まり、エラーを出さずに食い違ったまま残った。ユーザが 500 人を超えることは想定しないが（その規模なら別の製品を検討すべきである）、まるごとの送り直しにはユーザ以外のエントリも含まれる。
  - 複製用の DN にだけ上限を外す形（`olcLimits`）も試作で動いたが、データと `cn=accesslog` の両方に書く必要があり、書き漏らすと同じく黙って壊れる。全体の上限を外せば、この落とし穴がなくなる。
  - 上限が守るもの（大量の結果による負荷、ツリーの持ち出し）は、Koitohan では効いていない。データは多くても数百件である。ツリー全体を読めるのは、`ldapi:///` の root とサービスアカウントと複製用の DN だけで、ユーザが 500 人を超えなければ、上限にかかる前に全員の分が取れる。ユーザは自分のエントリだけ、匿名は何も読めない。外しても、読める範囲は変わらない。
  - 複製以外で全件を検索するもの（4.7 節のスクリプトの番号の割り当て、利用者作業用コンテナの `koitohan-update-users`）は、上限にかかると `ldapsearch` が終了ステータス 4 で終わり、失敗として止まる。黙っては壊れない。
  - 時間の上限（`olcTimeLimit`。既定の 3600 秒）は変えない。つなぎっぱなしの複製の検索（`refreshAndPersist`）を切らないことを、試作で確かめた。全体の件数の上限を外し、`olcLimits` を書かない形で 76 分動かし、5 分ごとに両方の台へ書き込んだ。始め直しは一度もなく、どの回も揃った。
  - 稼働中の環境にも効くように、TLS の下限（4.5 節）と同じく、起動のたびに `slapmodify` で書く。
  - スモークテストでは、上限を超える件数で確かめる。
- 既存のサービスアカウント（FreeRADIUS、利用者作業用コンテナ）も、同じく証明書だけで足りうる。いまのパスワードは、証明書の秘密鍵と同じ場所に同じ権限で置いてあり、独立した守りになっていない。移すかどうかは、冗長構成とは別の課題とする。

試作（1台の Docker ホストに2つの OpenLDAP。2つの CA、LDAPS、TLS 1.3、クライアント証明書を必須に。2台目は空から始め、1台目には件数の上限を超える 604 件を持たせた）で、次のことを確かめた。複製用の DN にだけ上限を外した形（3 回）でも、全体の上限を外した形（1 回）でも同じだった。

| 確認                                                                         | 結果                     |
| ---------------------------------------------------------------------------- | ------------------------ |
| 空の2台目に全件が届き、パスワードで bind でき、ppolicy の失敗の記録も届く    | 届く                     |
| 複製用の証明書で、全件、`userPassword`、`cn=accesslog` を読む                 | 読める                   |
| 複製用の証明書で書き込む                                                     | 拒否される               |
| 同じ CA の、別の subject の証明書（FreeRADIUS にあたる）で読む                | ツリーも差分も 0 件      |
| 信頼していない CA の、同じ subject の証明書                                  | TLS で拒否される         |
| 対応づけた DN へのパスワードでの bind、証明書だけで bind しない匿名           | 拒否される、0 件         |
| 両方での書き込み、片方を止めているあいだの書き込み                           | 揃う                     |

**変更の差分（accesslog）**

変更の差分は 14 日持ち、1 日ごとに古いものを消す（`olcAccessLogPurge: 14+00:00 01+00:00`。2026-11-21 に決定）。差分のデータベース（`{2}mdb`）の大きさの上限（`olcDbMaxSize`）は 4 GiB にする。

- 変更の差分は、書き込み1回ごとに、どのエントリのどの属性をどう変えたかを残す。ppolicy の失敗の記録（`pwdFailureTime`）とは別物で、認証に1回失敗すると、失敗の記録に1つ足す変更が、差分の1件になる。
- 差分は、相手の台に渡したら消すのではなく、古くなったら消す。2台が揃っていても、保持期間の分は溜まる。消すのは slapd 自身で、起動から 1 日ごとに確かめる。実際に残るのは 14〜15 日分である。
- 相手の台が保持期間より長く離れていると、差分では追いつけず、エントリをまるごと送り直す形に切り替わる。
  - 片方の台が止まっていた場合は、何日止まっていても揃う。
  - 両方の台が動いたまま切れていた場合は、同じエントリを両側で変えると、新しいほうがエントリごと勝ち、古いほうの変更は消える（通常の syncrepl と同じ）。たとえば、片方の台でパスワードを変えたあと、もう片方の台でその人が認証に失敗すると、パスワードの変更が戻りうる。
  - したがって保持期間は、2台が切れたことに気づいて直すまでの猶予である。Koitohan の監視は環境によって違うので、長い休みをまたげるよう 14 日とした。
- 差分が増えるのは、書き込みと、存在するユーザの認証の失敗だけである。成功した認証、ロック中の失敗、存在しないユーザへの試行では増えない。1件はディスクで約 4 KiB である。
  - 総当たりを受けても、ロック（4.8 節。既定は 10 回の失敗で 300 秒）があるので、1人あたり 300 秒に 10 件ほどにとどまる（1日に約 12 MiB、14 日で約 170 MiB）。リトライの間隔が効くのは、ロックに届くまでの速さだけである。4 GiB は、約 24 人が 14 日間狙われ続けても届かない大きさである。
  - 上限は予約で、使った分だけディスクを使う。データのデータベースの上限（1 GiB。`openldap/build/entrypoint.sh`）とは別に書く。
  - SD カードへの書き込みも、狙われ続けて1人あたり1日約 12 MiB で、寿命への影響は小さいと見ている。
- 上限に達すると、複製は黙って壊れる。データの書き込みは成功するのに差分が書けず（`MDB_MAP_FULL`）、その変更は相手の台に届かないまま食い違う。上限を書かなければ既定の 10 MiB で、狙われたユーザ1人で1日のうちに届く。
- ファイル（`data.mdb`）は、古い差分を消しても縮まない（LMDB の性質。空いた領域は次の書き込みに使い回す）。総当たりのあとは、そのときの大きさのまま残る。縮めるのは、slapd を止めて `mdb_copy -c` で作り直す手作業とし、自動にはしない（手順は実装のときに確かめる）。
- 稼働の確認（8 節）に、2台が揃っていないこと、差分のデータベースが上限に近いことの2つを WARN として足す。黙って壊れる2つの場合（長い切断、上限への到達）に、1日のうちに気づけるようにする。総当たりそのものに気づく確認（ロック中のユーザなど）は、冗長構成とは別の課題とする。
- バックアップ（8 節）には入れない。データは `slapcat` で取れ、差分は複製のためだけのものである。

試作（「複製の身元」と同じ2台。保持期間を 2 分に縮め、差分が消えたあとで再びつないだ。各 1 回）で、次のことを確かめた。

| 確認                                                                         | 結果                                               |
| ---------------------------------------------------------------------------- | -------------------------------------------------- |
| 片方を止めているあいだに、もう片方で追加、削除、変更、認証の失敗             | 揃う                                               |
| 両方が動いたまま切れ、両方で別々のエントリに追加、削除、変更、認証の失敗     | 揃う（片方で足したエントリが送り直しで消されない） |
| 両方が動いたまま切れ、同じエントリの別々の属性を両側で変える                 | 新しいほうが勝ち、古いほうの変更は消える           |
| 短い切断                                                                     | TCP の接続が残り、つながり直すと届く（注）         |
| ロック中の失敗、成功した認証、存在しないユーザへの試行                       | 差分は増えない                                     |
| 差分のデータベースの上限を 1 MiB にして、認証の失敗で埋める                  | データは変わるが相手に届かず、食い違ったまま       |

注: そのため、両方が動いたまま切れる2つの確認は、切れているあいだに両方を再起動して、接続を作り直させた。

**番号（`uidNumber`）**

`cn=nextUidNumber` のカウンタ（4.7 節）を2台で同時に進めると、同じ番号を取りうる。ユーザの管理は片方の台で行う、という運用の決まりで避ける（2026-11-05 に決定）。台ごとに範囲を分ける方式は、要望が上がれば検討する。

同じ決まりで、ロールの食い違いも避ける。4.7 節のスクリプトのロールの変更は、終わったあとにロールを1つにするが、今のロールを読んでから書き換えるまでのあいだに入った変更は見ない。2台で同時に同じユーザのロールを変えると（たとえば A の台で `admin` に、B の台で `readonly` に）、どちらのスクリプトも正常に終わり、複製で合わさったあとには2つのロールを持つ。そのときは、いちばん弱いロールとして扱われる（5.3 節）。

**証明書**（2026-10-13 に方針を決めた）

- 共通の CA は置かない。各台が自分の CA を持ち（4.5 節）、CA の証明書を帯域外の方法で互いに渡して、信頼の起点にする。CA の秘密鍵を残したり運んだりしなくて済み、発行のあとに秘密鍵を消す設計（4.5 節）と合う。
- サーバ証明書の SAN に、相手の台から見える Docker ホストの IP アドレスを入れる（`IP:` の型）。DNS を持たないこのスタックで、認証を DNS に依存させないため、FQDN にはしない。コンテナ名の `DNS:` は残す。
- 各台の CA は、複製用のクライアント証明書（「複製の身元」の項）も発行する。subject は、ほかの証明書と重ならない決まった形にする（試作では `CN=replication,OU=<台>,O=koitohan`）。受ける側は subject だけで見分けるので（発行した CA は見ない）、`scripts/create_certs.sh` が作るほかの証明書の subject と重ならないように保つ。
- 残る検討点:
  - `make certs` で CA を作り直すたびに、相手の台への配り直しが要る。アドレスを変えたときも同じである。
  - 相手の台の CA が発行したクライアント証明書は、すべて TLS を通るようになる。クライアント証明書は入口の関門で、権限は bind で決まる（4.3 節）。複製用の証明書だけは、bind そのものが証明書で決まる。
  - 取り消しは CA の単位になる。CA の秘密鍵は発行のあとに消すので（4.5 節）、1枚だけを取り消す手段がない。複製用の証明書の秘密鍵が漏れたときは、その台の CA ごと作り直し、相手の台に CA の証明書を配り直す。パスワードなら1つだけを替えられるが、漏れる場所は秘密鍵と同じである（「複製の身元」の項）。
  - 試作は Koitohan の外で組んだ。実装のときは、`scripts/create_certs.sh` での subject の組み立てと、`ldaps://` の相手を IP アドレスで指したときの SAN の照合を確かめる。

**検討中の項目**

- **FreeRADIUS から見た OpenLDAP**: 各台の FreeRADIUS は、自分の台の OpenLDAP だけを使う。自分の台の OpenLDAP が止まると、FreeRADIUS は応答せず、機器がもう1台へ切り替える（5.8 節）。  
  FreeRADIUS が両方の台の OpenLDAP を使い、片方が止まったら同じ要求をもう片方へ回す形にすれば、機器のタイムアウトを待たずに済む。その形を採るときは、5.8 節の設定（要求を待たせる）を見直す。すぐに失敗するほうが、回すのが速い。
- **2台目の始め方**: 2台目は、データのデータベースを空のまま起動し、複製で1台目からまるごと受け取る（2026-11-21 に決定）。
  - 2台がそれぞれ初期投入（4.6 節）すると、同じ DN のエントリが別の `entryUUID` と `entryCSN` を持ち、複製で衝突する。2台目は、`cn=config` だけを自分で作り、データの初期投入（サフィックス、`ou`、ロール、パスワードポリシー）はしない。
  - 当初は、1台目のバックアップ（`slapcat`）から始める案だった。試作で、この案は食い違いを残すことがわかった（3 回中 3 回）。バックアップの `contextCSN` は実際より古く（syncprov がデータベースに書くのはチェックポイントのときだけ、と見ている。未確認）、2台目はその時点から変更を再生しようとして、バックアップに含まれている削除でつまずく。差分での同期をあきらめてエントリをまるごと送り直すが、そこでバックアップのあとの削除が漏れ、消したはずのエントリが2台目にだけ残り続ける。
  - 空から始める形は、試作で 3 回とも揃った。空の2台目から1台目への複製で、1台目のエントリが消されることもなかった。試作の1台目には、Koitohan と同じく `slapadd` で入れた、変更の差分を持たないデータを持たせた。ppolicy の失敗の記録と `entryUUID` も揃い、両方での書き込み、両方の再起動、片方を止めているあいだの書き込みのあとも揃った。
  - 初期投入の LDIF（4.6 節）は、`cn=config` への書き込み（400 の ppolicy のオーバーレイ、900 のアクセス制御）とデータを1つのファイルに混ぜている。2台目は前者だけを使うので、分ける。
  - 2台目のサービスアカウント（「サービスアカウント」の項）は、複製で `ou=ServiceAccounts` が届いてから足す。足したエントリは、複製で1台目にも届く。
  - 受け取り終えるまでは、ユーザが見つからず、認証が拒否される。受け取り終えるまで LDAPS（636/tcp）で待ち受けないなど、その間の扱いを決める。
  - 1台で動いている Koitohan に、あとから複製の設定（`olcServerID`、`syncprov`、accesslog、相手を向いた `syncrepl`）を足す手順は、まだ試していない。試作の1台目は、最初から複製の設定で起動した。
- **経路**: 636/tcp は Docker ホストで公開済みで、ホストの外からは `OPENLDAP_ALLOWED_NETWORKS` のアドレスだけを受け付ける（8 節の「接続元の制限」。2026-11-21 に実装）。2台の構成では、各台に相手の台のアドレスを書く。残りは、イメージに `syncprov` と `accesslog` のオーバーレイのパッケージを足すことである。
- **復元**: 片方の台を古いバックアップで戻しても、相手の台から新しい状態（誤って消したエントリの削除を含む）が届く。誤操作を戻すには、両方の台を止める手順が要る。  
  加えて、2台目の始め方で見たとおり、バックアップから戻した台は、相手の台と食い違ったまま残りうる。2台の構成での復元は、片方の台をバックアップから戻し（8 節）、もう片方の台はデータを空にして、2台目の始め方と同じく複製で入れ直す形にする案である。片方の台が壊れただけのときは、バックアップを使わず、その台を空から入れ直せばよい。
- **時計**: 複製の順序は `entryCSN` の時刻に頼る。Docker ホストの時刻の同期は、`make host_check` が確かめている（3.6 節）。

**開発と確認**

- 開発は1台の Docker ホストで行い、OpenLDAP を2つ並べて複製させる。スモークテストも同じ形で、1台の上で2つの OpenLDAP を動かす（GitHub Actions のランナーでも動かせる）。
- 1台では確かめられないもの（SAN の IP アドレス、CA の受け渡し、636/tcp の絞り込み、ネットワークの断）は、2台の Raspberry Pi で確かめる。
