# Koitohan 基本設計書

[基本設計書（概要と目次）](../basic-design.md)の一部。「N 節」という参照は、目次から章のファイルをたどる。

## 4. LDAP ディレクトリ構造（基本設計）

```text
dc=example,dc=com
 ├── ou=People
 │     └── uid=alice
 ├── ou=Roles
 │     ├── cn=admin
 │     ├── cn=operator
 │     └── cn=readonly
 └── ou=Policies
        └── cn=default
```

サフィックスは `.env` の `LDAP_DOMAIN` から決まる（`example.com` → `dc=example,dc=com`）。  
`ou=People` は空の状態で構築し、ユーザは構築のあとで登録する（4.7 節）。`uid=alice` はその例である。検証用のテストアカウントは初期投入に含めず、スモークテストが自分のスタックの中に作る（5.6 節）。

### 4.1 ロール

ロールは `ou=Roles` 直下の `groupOfUniqueNames` で表現し、ユーザの所属は memberOf オーバーレイにより `memberOf` 属性として参照する。

```text
uid=alice
memberOf: cn=admin,ou=Roles,dc=example,dc=com
```

ロールはベンダーに依存しない。ベンダーごとの権限への読み替えは FreeRADIUS が行う（5 節）。

### 4.2 サービスの身元

FreeRADIUS と利用者作業用コンテナ（7 節）は、クライアント証明書（4.5 節）だけで OpenLDAP に bind する（SASL EXTERNAL。2026-11-22 に決定し、実装済み）。サービスアカウントのエントリとパスワードは置かない。

以前は、`ou=ServiceAccounts` にパスワードのアカウント（`uid=radius`、`uid=openssh`）を置き、クライアント証明書で TLS を通したうえで、パスワードで simple bind していた。次の理由で改めた。

- パスワードは、独立した守りになっていなかった。パスワードは、証明書の秘密鍵と同じ場所に、同じ権限で置いてあった（Docker ホストでは 0700 のディレクトリ、コンテナの中では root か bind するプロセスだけが読める場所）。鍵を読める相手は、パスワードも読める。
- パスワードに付随する仕組みがなくなる。`secrets/` のファイル、生成と変更のスクリプト（4.10 節）、ppolicy のロックの例外（4.8 節）、設定ファイルに書く平文のパスワード（FreeRADIUS の LDAP モジュール設定、`nslcd.conf`）である。
- 冗長構成（12 節）で、台ごとのアカウントを作り、相手の台へ届ける手順が要らない。相手の台の CA を信頼していれば、相手の台の FreeRADIUS も、同じ身元になる。

失うものは、身元を1つだけ取り消す手段である。CA の秘密鍵は発行のあとに消すので（4.5 節）、証明書の秘密鍵が漏れたときは、CA ごと作り直す。パスワードなら1つだけを替えられたが、漏れる場所は秘密鍵と同じだった。

**対応づけ**

OpenLDAP は、クライアント証明書の subject を、決まった DN に対応づける（`olcAuthzRegexp`）。

| サービス             | 証明書の subject                     | 対応づける DN               |
| -------------------- | ------------------------------------ | --------------------------- |
| FreeRADIUS           | `CN=freeradius,OU=<台>,O=koitohan`   | `cn=freeradius,cn=koitohan` |
| 利用者作業用コンテナ | `CN=openssh,OU=<台>,O=koitohan`      | `cn=openssh,cn=koitohan`    |

- DN のエントリは置かない。パスワードもない。アクセス制御（4.3 節）に、この DN を書く。
- `OU` は、対応づけでは見ない。どの台の CA が発行した証明書も、同じ DN になる。`OU` は、どの台からの接続かを、ログで見分けるためのものである。値は、証明書を作るときの Docker ホストの短いホスト名（`hostname -s`）にする。`.env` に変数を足さずに、台ごとに違う値になる。
- subject は、以前の形（`DC=<コンテナ名>,<サフィックス>`）から、冗長構成の複製用の証明書（12.1 節）と同じ形に改める。
- 発行した CA は見ない。OpenLDAP が信頼する CA（自分の台の CA。冗長構成では相手の台の CA も）が発行した証明書なら、subject だけで決まる。決まった形でない subject の証明書でも bind はできるが、subject そのものが身元になり、アクセス制御に書いていないので何も読めない。
- 対応づけとアクセス制御は、起動スクリプトが起動のたびに書く（TLS の下限と同じ。4.5 節）。`ldapi:///` から書き換えても、次の起動で戻る。

### 4.3 サービスのアクセス制御

サービスの2つの DN（4.2 節）には、次の権限を与える。

- サフィックスの下の読み取り
- ただし `userPassword` は除く（先行するアクセス制御により、本人と管理者のほかは読めない）

これにより、FreeRADIUS と利用者作業用コンテナは、ユーザ情報（`uid`、`memberOf` など）を参照できるが、パスワードの値そのものを読み取ることはできない。書き込みの権限は与えない。

以前は、`ou=ServiceAccounts` の下のすべてのエントリに読み取りを与えていた（`dn.subtree`）。そこにエントリを置くだけで、ツリー全体を読めるようになっていた。いまは、2つの DN だけを書く。

### 4.4 FreeRADIUS と利用者作業用コンテナの bind

FreeRADIUS は、証明書の身元（4.2 節）で bind して、次を行う。

- ユーザ DN の検索
- `memberOf` の取得

ユーザの認証は、検索で得た DN とユーザが入力したパスワードで bind して行う（以前と同じ）。

- FreeRADIUS の LDAP モジュール設定には、`identity` と `password` を書かず、`sasl { mech = 'EXTERNAL' }` を書く。
- 利用者作業用コンテナでは、`nslcd` が `sasl_mech EXTERNAL` で（`binddn` と `bindpw` は書かない）、`koitohan-update-users` が `ldapsearch -Y EXTERNAL` で bind する。ユーザの一覧の取得と、認証のためのユーザ DN の検索に使う。

試作（2026-11-22。Koitohan のイメージの OpenLDAP に、対応づけと読み取りの1行だけを足した。FreeRADIUS と利用者作業用コンテナは、リポジトリの設定から、パスワードの部分だけを替えた）で、次のことを確かめた。

| 確認                                                                         | 結果                                                       |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| FreeRADIUS と `nslcd` の bind                                                | 対応づけた DN で、`mech=EXTERNAL`。simple bind は 0 回     |
| RADIUS: 正しいパスワード、誤ったパスワード、存在しないユーザ                 | Accept（ロールの応答属性も届く）、Reject、Reject           |
| RADIUS: 相手の台の CA が発行した FreeRADIUS の証明書                         | 同じく通る                                                 |
| RADIUS: 同じ CA の、別の subject（複製用）の証明書                           | bind はするが、ユーザを読めず Reject                       |
| SSH: ログイン、誤ったパスワード、ロールのグループ                            | 入れる、拒否される、ロールのグループに入っている           |
| SSH: あとから足したユーザ（`koitohan-update-users`）、本人の `passwd`        | 次の周期で入れる、変えたパスワードで入れる                 |
| OpenLDAP の再起動のあとの最初のログイン（RADIUS と SSH）、FreeRADIUS の再起動 | 通る                                                       |

### 4.5 TLS

LDAP の通信はプライベート CA による TLS で保護する。

- プライベート CA を構築時に作成する。
- OpenLDAP にサーバ証明書を発行する（SAN はコンテナ名、FQDN、localhost）。
- FreeRADIUS と利用者作業用コンテナに、それぞれクライアント証明書を発行する。この証明書は、bind の身元を兼ねる（4.2 節）。
- OpenLDAP は、接続してくる相手にクライアント証明書を要求する。
- 待ち受けは 636（LDAPS）と、コンテナ内の UNIX ソケット（`ldapi:///`）だけにする。389 は待ち受けない。  
  TLS は 1.3 に限る（`olcTLSProtocolMin: 3.4`）。つなぐのはこのスタックの FreeRADIUS と利用者作業用コンテナだけで、どちらも TLS 1.3 を使う。TLS 1.2 を残すと、前方秘匿性のない鍵交換（静的 RSA）も受け付けることになる。  
  DH パラメータのファイル（`olcTLSDHParamFile`）は置かない。これを使うのは TLS 1.2 の DHE の暗号スイートだけで、TLS 1.3 の鍵交換は名前付きのグループで決まる。  
  TLS の下限は、起動スクリプトが起動のたびに設定へ書く。`ldapi:///` から書き換えられても、次の起動で戻る。  
  加えて、TLS を使わない操作を拒否する設定（`olcSecurity: ssf=128`）を入れてある。待ち受けを誤って増やしても、平文では操作できない。  
  `ldapi:///` は対象外で、初期投入と保守に使える。
- 証明書と秘密鍵は、root だけが入れるディレクトリに読み取り専用でマウントし、起動時に `slapd` 専用のディレクトリ（tmpfs）へ写す。`slapd` は降格したあとで読むためである。Docker ホストのファイルの所有者は変えない。
- 証明書の名前はコンテナ名から決まるため、コンテナ名を変えたら証明書を作り直す。

証明書はこのスタックのコンテナ間でのみ使用し、外部には配布しない。そのため、再構築時は CA ごと作り直してよい。

鍵の扱いは次のとおりである。

- CA の秘密鍵は、証明書を発行したあとに消す。作り直しのたびに CA から作るので、発行のあとに使う場面がない。残しておくと、盗まれたときに、OpenLDAP が受け入れるクライアント証明書を作られる。証明書署名要求（CSR）も残さない。
- 鍵を置くディレクトリ（`CA/`）は、所有者しか入れないようにする（0700）。`make` と `make up` が設定する。sshd のホスト鍵を置く `openssh/hostkeys/` も同じにする。管理者のパスワードを置いていた `secrets/` も同じにしていたが、パスワードとともに廃止する（4.11 節）。
- FreeRADIUS のクライアント証明書の鍵だけは、ファイルのパーミッションを 0644 にしている。FreeRADIUS が、権限を落としたあと（コンテナ内の uid 101）で読むためである。Docker ホストのほかのユーザから読めないことは、ディレクトリのパーミッションで保っている。  
  ファイル単体のバインドマウントは、Docker ホスト側の親ディレクトリのパーミッションに左右されないので、コンテナからは読める。  
  所有者を uid 101 に変える方法は採らない。作り直しのたびに Docker ホストの root の権限が要るようになり、得られるものは変わらない。

### 4.6 初期投入

OU、ロール、パスワードポリシーは LDIF として生成し、OpenLDAP の初回起動時（データベースが空のとき）に投入する。  
投入内容を変更して再投入するには、永続化したデータベースを削除する必要がある。

投入はイメージの起動スクリプト（`openldap/build/entrypoint.sh`）が行う。

- 設定（`cn=config`）とサフィックスのエントリは、スクリプトが作る。スキーマ、`memberOf` と参照整合性のオーバーレイ、TLS の設定はここに含まれる。サービスの対応づけとアクセス制御（4.2 節、4.3 節）は、起動のたびにスクリプトが書く。
- 続いて、生成した LDIF をファイル名の順に入れる。このあいだ `slapd` は `ldapi:///` だけで待ち受けるので、投入の途中のディレクトリには外から届かない。
- 1つでも失敗したら、作りかけの設定とデータを消して終了する。欠けたディレクトリで待ち受けないためである。LDIF を直せば、次の起動でやり直せる。
- 最後まで済むと、設定のディレクトリに目印のファイル（`koitohan-seeded`）を置く。目印があれば、以降の起動では投入しない。
- 目印がないのに設定かデータが残っているとき（投入の途中で止められた、別のイメージが作った）は、起動しない。消すと中身が失われるので、スクリプトは消さず、こいとはん管理者に判断を委ねる。

4.7 節以降の項目には、スキーマやオーバーレイの追加を伴うものがある。  
これらは空のデータベースにしか投入されないため、稼働中の環境に対しては、データベースを消さずに適用する手順を別に用意する（パスワードポリシーの手順は 4.8 節）。

### 4.7 ユーザの管理

ユーザの登録・削除とロールの割り当ては、こいとはん管理者が Docker ホスト上のスクリプトで行う。管理用の画面は設けない。

- こいとはん管理者はホストのシェルを使えるため、画面がなくても作業できる。
- スクリプトは、本プロダクトのモデルに合わない登録を受け付けない。  
  汎用の LDAP 管理ツールでは、この制約を強制できない。
- ユーザに割り当てるロールは1つとする。スクリプトを通さずに複数のロールに所属させたユーザは、そのうちいちばん弱いロールとして扱われる（5.3 節）。
- 初期パスワードはこいとはん管理者が発行し、ユーザ本人が利用者作業用コンテナで変更する（7.5 節）。
- 発行するパスワードにも、4.8 節の規則を適用する。
- ユーザの登録、削除、ロールの変更のたびに、利用者作業用コンテナの `/etc/passwd` と `/etc/group` を作り直させる（7.2 節）。作業した台では、周期を待たずに効く。
- ユーザの削除とロールの変更では、そのユーザのログイン中のセッションが切れる。切るのは作り直しの側で、スクリプトは自分では切らない（7.2 節）。

提供する操作は、ユーザの登録、削除、ロールの変更、パスワードの再発行、ロックの解除とする。

**実装（`bin/manage_users.sh`）**

| 操作               | コマンド                        |
| ------------------ | ------------------------------- |
| 登録               | `add <ユーザ> <ロール> [<氏名>]` |
| 削除               | `delete <ユーザ>`               |
| ロールの変更       | `role <ユーザ> <ロール>`        |
| パスワードの再発行 | `passwd <ユーザ>`               |
| ロックの解除       | `unlock <ユーザ>`               |

- Docker ホストで実行し、作業はコンテナの中で行う。LDAP の操作は OpenLDAP のコンテナの `ldapi:///` から、パスワードの判定は利用者作業用コンテナの `pwqcheck` で行う。Docker ホストに追加で要るものはない。
- 登録で受け付けないもの: ログイン名として使えない名前（`koitohan-update-users` と同じ規則。7.9 節）、すでにあるユーザ、利用者作業用コンテナのイメージに元からあるアカウントと同じ名前、3つのロール以外のロール。
- パスワードは端末から2回尋ねる。端末がないときは、標準入力の1行目を読む。引数では受け取らない（`ps` で見えるため）。
- `pwqcheck` には、ユーザ名と氏名も渡す。これらをもとにしたパスワードは拒否される。
- パスワードは、パスワード変更の拡張操作（`ldappasswd`）で、平文のまま標準入力から渡す。ハッシュ化は OpenLDAP が行う。エントリの追加に `userPassword` を含めないのは、ppolicy をまだ適用していないデータベース（4.8 節）では、平文で書いた値がそのまま保存されるためである。
- 登録は、エントリの追加、パスワードの設定、ロールへの追加の順に行う。途中で失敗したときは、エントリを削除する。割り当てた `uidNumber` は戻さない（4.9 節）。
- ロールの変更は、新しいロールへの追加、元のロールからの削除の順に行う。途中で失敗しても、ロールのないユーザにはならない。複数のロールに所属しているユーザ（スクリプトを通さずに作られたもの）も、指定したロール1つにまとめる。
- ロックの解除は、`pwdAccountLockedTime` と `pwdFailureTime` を削除する。失敗の記録も消すのは、残しておくと、次の1回の失敗でふたたびロックされるためである。`pwdFailureTime` は通常の変更を受け付けないので、relax 制御を付ける。
- 削除、ロールの変更、パスワードの再発行、ロックの解除は、スクリプトを通さずに作られたユーザも対象にできる。
- スモークテスト（`make test`）で、すべての操作と、受け付けない登録を確かめる。

### 4.8 パスワードポリシー

実装済みである。複雑さは、利用者作業用コンテナの `passwd` と 4.7 節のスクリプトが判定する（`.env` の `PASSWDQC_MIN`）。最小の長さとロックは、OpenLDAP の ppolicy オーバーレイが強制する（`.env` の `PPOLICY_*`）。

**複雑さ**

文字の種類を一律に強制することはしない。短いパスワードにだけ文字の種類を求め、長ければ種類を問わない。

| 含む文字の種類 | 最小の長さ |
| -------------- | ---------- |
| 3種類以上      | 8          |
| 2種類          | 10         |
| 1種類          | 12         |

文字の種類は、大文字・小文字・数字・その他の4つである。値は既定値であり、`.env` で変更できるようにする。

判定には passwdqc を使う。上の表は `min=12,10,10,8,8` にあたる。  
passwdqc は、先頭の大文字と末尾の数字を種類に数えない。たとえば `Password1` は1種類として扱われる。ありがちな水増しを防ぐための仕様であり、表を素朴に読んだ場合よりも厳しくなる。

passwdqc は Alpine のパッケージとしては入手できないので、利用者作業用コンテナのイメージのビルドの中で、ソースからビルドする。バージョン（2.1.0）とチェックサムは Dockerfile で固定する。  
4.7 節のスクリプトも、このコンテナの中の `pwqcheck` を呼んで判定する。Docker ホストには入れない。判定の設定を1か所にするためである。

**強制する場所**

| 場所                                           | 強制する内容                   |
| ---------------------------------------------- | ------------------------------ |
| パスワードを設定する入口（4.7 節、7.5 節）     | 上の表のすべて                 |
| OpenLDAP（ppolicy オーバーレイ）               | 最小の長さ（8 文字）とロック   |

表のとおりの判定を OpenLDAP 自身に行わせるには、判定用のモジュールを組み込んだイメージを自前でビルドする必要があり、本プロダクトの規模に合わないため採用しない。

そのため、利用者作業用コンテナのシェルを使えるユーザは、入口の判定を通さずに自身のパスワードを書き換えることができる。その場合でも、OpenLDAP が保証する最小の長さは守られる。  
この規則の目的は、不注意で弱いパスワードを設定することを防ぐことにあり、意図して迂回するユーザまでは対象としない。この制約は README の既知の問題にも記載する。

**ロック**

認証に続けて失敗したアカウントを、一定時間ロックする。

| 項目               | 既定値 | `.env` の変数（時間は秒で指定） |
| ------------------ | ------ | ------------------------------- |
| 失敗の回数         | 10 回  | `PPOLICY_MAX_FAILURE`           |
| 失敗を数える期間   | 5 分   | `PPOLICY_FAILURE_WINDOW`        |
| ロックする時間     | 5 分   | `PPOLICY_LOCKOUT_DURATION`      |

値は `.env` で変更できる。OpenLDAP が保証する最小の長さも同様である（`PPOLICY_MIN_LENGTH`）。

- FreeRADIUS も利用者作業用コンテナも LDAP の bind で認証するため、失敗の回数は両者で共通に数えられる。
- ロックは時間の経過で解除される。こいとはん管理者がスクリプトで解除することもできる（4.7 節）。
- サービスは証明書で bind するので（4.2 節）、ロックの対象になるアカウントを持たない。  
  以前は、FreeRADIUS のサービスアカウントがロックされるとすべてのユーザの認証が止まるので、ロックのないポリシーを割り当てていた。

ネットワーク機器のログイン画面に到達できる相手は、誤ったパスワードを送り続けることで、任意のユーザをロックできる。ロックを時間で解除するのは、この影響を一時的なものに留めるためである。

**実装（`openldap/ldif/400-PPolicy.ldif`）**

- `scripts/generate_ldap_base.sh` が `.env` から生成し、初期投入（4.6 節）に含める。番号は、ロールの LDIF（`200`）のあとである。以前は、ハッシュ済みのパスワードを持つサービスアカウントの LDIF（`300`）を先に入れる必要があった（7.7 節）が、サービスアカウントとともに、この順序の制約もなくなった。
- ファイルの中は、モジュールの読み込み、オーバーレイの追加、ポリシーのエントリの順である。
- ポリシーは `ou=Policies` に1つ置く（`cn=default`）。オーバーレイの既定のポリシー（`olcPPolicyDefault`）で、割り当てのないエントリすべてに効く。最小の長さとロックを持つ。以前は、ロックを無効にした `cn=serviceaccounts` も置いていた（4.2 節）。
- `pwdCheckQuality` は `2` にする。ハッシュ済みの値は長さを確かめられないので、拒否する（7.7 節）。  
  このため、適用のあとは、ハッシュ済みのパスワードを持つエントリを追加できない。
- 平文で書き込まれた値は OpenLDAP がハッシュ化する（`olcPPolicyHashCleartext`）。ロックされていることは相手に伝えない（`olcPPolicyUseLockout: FALSE`）。
- 稼働中のデータベースには、コンテナ内の `ldapi:///` から同じファイルを適用する。データベースを消す必要はない。
- 適用し直せるように、ポリシーの値は、エントリの追加とは別の、置き換えの変更として書いてある。`.env` の値を変えたときは、LDIF を生成し直して `ldapmodify -c` で適用する。すでにあるモジュール、オーバーレイ、エントリの追加はエラーになるが、`-c` で先へ進み、値だけが置き換わる。
- スモークテスト（`make test`）で、次を確かめる。
  - 最小の長さに満たないパスワードと、ハッシュ済みの値を、ユーザ本人が OpenLDAP に直接書き込もうとして拒否されること。
  - RADIUS で失敗を重ねたユーザが、正しいパスワードでも、RADIUS と SSH の両方で拒否されること。スクリプトでロックを解除すると、両方で通ること。
  - 利用者作業用コンテナの `passwd` と 4.7 節のスクリプトが、ppolicy を有効にした OpenLDAP に対して働くこと（従来の確認が、そのままこれにあたる）。

### 4.9 posixAccount

利用者作業用コンテナも、番号を割り当てるスクリプト（4.7 節）も、この節の属性を前提として実装済みである。

`ou=People` のユーザに、`inetOrgPerson` に加えて `posixAccount` を持たせる。

利用者作業用コンテナでは、ユーザが書き込んだファイルが、UID の数値のまま Docker ホストのディスクに残る。番号を LDAP で管理することで、コンテナを作り直してもファイルの所有者が変わらない。

| 属性            | 値                                     |
| --------------- | -------------------------------------- |
| `uidNumber`     | 10000〜59999 から、登録順に割り当てる  |
| `gidNumber`     | 10000（全ユーザ共通のグループ）        |
| `homeDirectory` | `/home/<uid>`                          |
| `loginShell`    | `/bin/sh`                              |

- 10000 から始めるのは、Docker ホストとコンテナが使う番号を避けるためである。  
  システムのアカウント（999 以下。FreeRADIUS の 101、OpenLDAP の 100 を含む）、ホストの一般ユーザ（1000 以降）、systemd が使う範囲（60001 以降）、ユーザ名前空間の subuid（100000 以降）のいずれとも重ならない。
- 番号は再利用しない。削除したユーザのファイルは数値のまま残るので、同じ番号を別のユーザに割り当てると、そのファイルが新しいユーザのものになる。
- そのため、次に割り当てる番号は LDAP に記録する。「使用中の最大値 + 1」では、最後に登録したユーザを削除したときに再利用が起きる。
- 番号の割り当ては 4.7 節のスクリプトが行う。
  - 次に割り当てる番号は、サフィックスの直下のエントリ `cn=nextUidNumber` の `serialNumber` に置く。`objectClass` は `device` である。OpenLDAP の標準のスキーマだけで作れるものを選んだ。
  - 割り当ては、読んだ値の削除と、次の値の追加を、1回の変更で行う。同時に実行された別の割り当てが同じ番号を取っていれば、削除が失敗するので、読み直してやり直す。
  - このエントリは初期投入に含めず、最初の登録のときにスクリプトが作る。初期値は、その時点で使われている最大の番号の次（ユーザがいなければ 10000）である。稼働中の環境にも、そのまま導入できる。  
    スクリプトを使い始める前に削除されたユーザの番号までは分からない。その範囲では、再利用が起こりうる。

ロールは `groupOfUniqueNames` のままとし、`posixGroup` にはしない。OS のグループへの対応づけは、利用者作業用コンテナの中で行う（7.2 節）。

`posixAccount` を持たせておくと、ほかの Linux ホストなどの認証にも同じディレクトリを使える余地がある。これを提供するかどうかは未決定である（13 節）。

### 4.10 サービスアカウントのパスワード

廃止した（2026-11-22 に決定し、実装済み）。サービスは証明書だけで bind し（4.2 節）、パスワードを持たない。

以前は、サービスアカウント（`uid=radius`、`uid=openssh`）のパスワードを、構築時にスクリプトが 48 桁の 16 進数で生成し、`secrets/` に置いていた（`make secrets`）。値は、初期投入の LDIF（ハッシュ）、FreeRADIUS の LDAP モジュール設定、利用者作業用コンテナ（ファイル単体のマウント）に渡し、稼働中の変更は `bin/change_service_account_password.sh` で行っていた。これらは、サービスアカウントとともに外した。

- 外したもの: `secrets/` の2つのファイル、生成のスクリプト（`scripts/generate_service_account_password.sh`）、変更のスクリプト、`.env` のアカウント名（`FREERADIUS_SERVICE_ACCOUNT_NAME`、`OPENSSH_SERVICE_ACCOUNT_NAME`）、初期投入の `300-ServiceAccounts` と `900-ACL`（前の版が生成したファイルは、生成のスクリプトが消す）、利用者作業用コンテナへのファイルのマウント。
- FreeRADIUS の LDAP モジュール設定は、パスワードを含まなくなったが、サフィックスを `.env` から決めるので、引き続き生成する。
- 稼働中の環境に残る古いエントリ（`ou=ServiceAccounts` とその下、ポリシーの `cn=serviceaccounts`）は、パスワードで bind できるまま残るので、消す。起動スクリプトは消さない。いまの実環境の利用者は少ないので、消すコマンドをリリースノートに書くだけにする（ユーザの判断）。

### 4.11 OpenLDAP の管理者のパスワード

廃止する（2026-11-23 に決定。実装はまだで、それまではパスワードのまま動く）。データの管理者（`cn=admin,<サフィックス>`）と設定の管理者（`cn=admin,cn=config`）は、どちらも rootdn だが、パスワード（`olcRootPW`）を置かない。管理の作業は、いまと同じく、コンテナの中の `ldapi:///` から、コンテナの root として行う（パスワードなしで管理者になる）。

理由は次のとおりである。

- 使う場面がない。このスタックのスクリプトは、`ldapi:///` だけを使う。636 番に管理者として bind するにはクライアント証明書が要るが（4.5 節）、外部の LDAP クライアントに出す証明書は発行しない。冗長構成の複製も、証明書の身元で bind する（12 節）。
- パスワードがなければ、推測も漏洩も起こらない。以前は、推測できない値にすることで、FreeRADIUS か利用者作業用コンテナが奪われても、管理者の権限までは渡らないようにしていた（下の「以前の形」）。パスワードがなければ、この心配そのものがなくなる。
- パスワードに付随する仕組みがなくなる。`secrets/` のディレクトリ、生成と変更のスクリプト、OpenLDAP へのマウント、バックアップの `secrets/`（8 節）、値をログに出さないための注意である。

失うものはない。Docker ホストに入れない人を管理者にする手段は、もとから提供していない（ユーザの管理は Docker ホストのスクリプトで行う。4.7 節）。

**設計**

- `olcRootDN` は残し、`olcRootPW` を置かない。パスワードがなければ、simple bind で rootdn にはなれない。証明書の対応づけ（4.2 節）も、rootdn には向けない。
- 起動スクリプトは、起動のたびに、`olcRootPW` があれば消す（`slapd` を起動する前の `slapmodify`。TLS の下限と同じところ）。以前の版で作ったディレクトリも、以前のバックアップから戻したディレクトリも、起動するだけでパスワードがなくなる。`ldapi:///` から書き込まれても、次の起動で消える。
- アクセス制御（4.3 節）から、`cn=admin,<サフィックス>` に書き込みを与える部分を外す。だれも bind できない DN だからである。
- 外すもの: `secrets/` のディレクトリ（`make secrets`、`make private_dirs` の対象、`make up` の依存）、`scripts/generate_ldap_admin_password.sh`、`bin/change_ldap_admin_password.sh`、OpenLDAP の `/etc/koitohan/secrets/` へのマウント、バックアップの `secrets/`。
- 稼働中の環境に残る `secrets/` のファイルは、使われなくなる。消してよいことを、リリースノートに書く。
- スモークテストで、`olcRootPW` がないこと、`ldapi:///` から書き込んでも次の起動で消えること、`cn=admin` で simple bind できないことを確かめる。

**以前の形**

構築時にスクリプトがパスワードを生成し、`secrets/` に置いていた（`ldap_admin_password`、`ldap_config_password`。48 桁の 16 進数）。OpenLDAP のコンテナにはファイル単体を読み取り専用でマウントし、起動スクリプトが起動のたびにハッシュ化して `olcRootPW` に書いた。稼働中の変更は `bin/change_ldap_admin_password.sh` で、2つを生成し直して OpenLDAP のコンテナを作り直した。

その前は `.env` に置いていた（`LDAP_ADMIN_PASSWORD`、`LDAP_CONFIG_PASSWORD`）。人が使う場面があると考えたためだが、人が決める値はサンプルの値のまま運用されうること、環境変数は `docker inspect` に表示されることから、生成する形に改めた。そのときに挙げた「実際には使う場面がほとんどない」ことを突き詰めて、今回、パスワードそのものを廃止する。

### 4.12 パスワードのハッシュ

実装済みである。OpenLDAP は、パスワードを Argon2id のハッシュ（`{ARGON2}`）で保存する。

以前は、OpenLDAP の既定のまま、ソルト付きの SHA-1（`{SSHA}`）で保存していた。次の理由で改めた。

- ハッシュは LDAP 越しには読めないが（4.3 節）、バックアップのアーカイブにはそのまま入る（8 節）。アーカイブは暗号化していない。
- アーカイブに入るほかの秘密は、それだけでは使いにくい。共有シークレットとホスト鍵は、通信に割り込める位置にいないと使えない。以前は管理者のパスワードも入っていたが、クライアント証明書がないと使えなかった（4.5 節。証明書はアーカイブに入れていない）。管理者のパスワードは廃止する（4.11 節）。  
  ユーザのハッシュだけは、アーカイブを手に入れた人が、手元で割り出しを試せる。
- SHA-1 は 1 回の計算が軽く、メモリも使わないので、GPU で大量に並べて試せる。passwdqc の規則（4.8 節）を通る 8 文字のパスワードは、総当たりで届く範囲にある。
- 割り出されたパスワードは、ユーザがほかの場所で使い回していると、Koitohan の外でも使われる。

Argon2 は、1 回の計算に決まった量のメモリを使わせる。試す数を並べるには、その数だけメモリが要る。正規の認証は 1 回の計算で済むので、守る側には軽く、割り出す側にだけ重い。

**パラメータ**

モジュールの既定（メモリ 7168 KiB、反復 5 回、並列 1）のままにする。Raspberry Pi 5（4 コア）で計測した値は、次のとおりである（2026-11-15。`ldapi:///` への simple bind、`slapd` の CPU 時間）。

| ハッシュ                          | bind 1 回 | 4 並列での上限 |
| --------------------------------- | --------- | -------------- |
| `{SSHA}`                          | 0.2 ms    | 毎秒 960 回    |
| Argon2id、7 MiB、5 回（既定）     | 37 ms     | 毎秒 53 回     |
| Argon2id、19 MiB、2 回            | 42 ms     | 毎秒 46 回     |
| Argon2id、64 MiB、3 回            | 207 ms    | 毎秒 9 回      |

- bind は、ログイン 1 回につき 1 回である。FreeRADIUS と `nslcd` の自分の bind は証明書によるもので（4.2 節）、Argon2 の計算を伴わない。
- メモリは、同時の bind の数だけ重なる。64 MiB では、16 並列（`slapd` のスレッドの既定の数）で 1 GB を超えた。OpenLDAP のコンテナにはメモリの上限がないので、メモリを増やす方向には変えない。
- パラメータはハッシュの中に記録され、照合はその値で行う。あとで変えても、すでにあるハッシュは照合できる。

**実装**

- イメージに `openldap-passwd-argon2` を入れ、`cn=config` でモジュール `argon2` を読み込み、フロントエンドのデータベースに `olcPasswordHash: {ARGON2}` を書く。
- 起動スクリプトは、初期投入のときだけでなく、起動のたびにこの 2 つを確かめて書く（TLS の下限と同じところ。4.5 節）。これにより、以前のイメージで作ったディレクトリも、以前のバックアップから戻したディレクトリも、イメージを替えて起動するだけで切り替わる。
- モジュールの読み込みは、方式の設定より先に書く。`slapmodify` は方式の名前を確かめずに書き込み、モジュールのない方式が書かれた設定は、`slapd` も `slapcat` も読めなくなる（試して確かめた）。
- すでにあるハッシュは書き換えない（平文がないので、書き換えられない）。認証には引き続き使え、次にパスワードを変えたときに Argon2id になる。
- 管理者のパスワード（`olcRootPW`）は `{SSHA}` のままにしていた（48 桁のランダムな値で、ハッシュの強さに頼っていなかった）。管理者のパスワードは廃止する（4.11 節）。
- 切り替えたあとのディレクトリは、モジュールのない以前のイメージでは起動しない。イメージを戻すときは、切り替える前のバックアップから戻すことになる。
- 冗長構成（12 節）では、`cn=config` は台ごとに持ち、どの台も同じイメージなので、台ごとに起動スクリプトが同じ設定を書く。
- スモークテスト（`make test`）で、スクリプトと `passwd` が設定したパスワードが `{ARGON2}` で保存されること、`ldapi:///` から方式を書き換えても次の起動で戻ることを確かめる。
