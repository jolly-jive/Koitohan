## 3. コンポーネント選定理由

### 3.1 OpenLDAP（ID管理）

**選定理由:**

- Raspberry Pi 5 でも軽量に動作する。
- Alpine のパッケージ（OpenLDAP 2.6。長期サポートのリリース）だけでイメージを組める。  
  当初は既製のイメージ（`osixia/openldap`）を使っていたが、中身が OpenLDAP 2.4 と Debian 10 のまま更新が止まっていたため、自前でビルドする形に改めた（8 節）。
- FreeRADIUS との連携が容易（`rlm_ldap`）。
- ロール管理を **memberOf（グループ）** で表現できる。
- 将来 Kerberos を導入する際にも自然に統合可能。
- 389 Directory Server は大規模・Red Hat 系向けで Pi には過剰。

**採用方針:**

- `ou=People` にユーザ。
- `ou=Roles` にロール（admin/operator/readonly）。
- 認証は当面 LDAP、将来 Kerberos へ拡張可能。
- 認可（権限）は RADIUS 側で決定。
- 待ち受けは LDAPS（636）のみとし、平文の 389 は待ち受けない（4.5 節）。

---

### 3.2 FreeRADIUS 4.x（認証・認可）

**選定理由:**

- LDAP の `memberOf` を参照してロール判定が可能。
- Cisco / Aruba / Allied などの VSA（Vendor-Specific Attribute）返却が容易。
- `unlang` で柔軟にポリシーを記述できる。
- Docker イメージが豊富で Pi 5 上でも十分軽量。
- 現時点で v4.x は、開発バージョンだが、複雑な機能を使う予定は無いため、正式リリースに先行して選定する。

**採用方針:**

- **機器種別 × ロール → 応答属性** を基本モデルとする（5 節）。
- 機器種別は、RADIUS クライアント定義（`clients.conf`）の `nas_type` で指定する。  
  Access-Request からは機器メーカーを確実には判定できないため、初版の「Vendor-ID による判定」から変更した。
- イメージ標準の設定をそのまま使い、Koitohan として書いた設定だけを読み取り専用で重ねる。

---

### 3.3 tftpd-hpa（TFTP）

**選定理由:**

- 軽量で Raspberry Pi に適する。
- ネットワーク機器のファームウェア配布やコンフィグ upload/download に適した実装。
- Alpine Linux のパッケージとして提供されており、小さなイメージ（約 9MB）を自前でビルドできる。  
  公式の Docker イメージは存在しないため、既存のイメージには依存しない。

**採用方針:**

- `/tftpboot` をホスト側ストレージに永続化。
- ファームウェア配布用ディレクトリ（`firmware/`）とコンフィグバックアップ用ディレクトリ（`configs/`）を階層分けする。
- `firmware/` は読み取り専用でマウントし、機器からの書き込み先を `configs/` に限定する。
- サーバは uid/gid 1000 で動作させ、ホスト側からそのままファイルを読み書きできるようにする。
- TFTP には認証がないため、書き込める容量を制限する（6.3 節）。
- 転送の記録（要求元とファイル名）をファイルに保存する（6.3 節）。
- PXE ブート環境は DHCP が前提となるため、11 節の判断に従う。

---

### 3.4 syslog-ng（ログ管理）

**選定理由:**

- ホスト別ログの分離が容易（フィルタ機能が強力）。
- ログローテーション・圧縮・長期保存の運用設計がしやすい。
- Docker イメージが安定しており、Pi 5 の NVMe と組み合わせて 3年保持が現実的。

**採用方針:**

- UDP/TCP 514 を開放し、ネットワーク機器からの SYSLOG を受信。
- ホスト名（または IP）ごとにログファイルを分割。
- 日次ローテーション＋圧縮＋3年間保持を基本ポリシーとする。
- ストレージは NVMe 256〜512GB を想定。

---

### 3.5 OpenSSH（ユーザの作業環境）

ユーザが、収集したログの閲覧と取得、TFTP のファイルの出し入れ、自身のパスワードの変更を行うための入口である。Web UI ではなく SSH とする。

**選定理由:**

- ログの取得前に `grep` / `sed` / `awk` などによる絞り込みを許したい。これはシェルそのものであり、Web で作り直すよりも、シェルを渡すほうが小さく済む。
- 「複数の機器の、特定の日付のログ」のような指定は、シェルの glob で書ける。
- ファイルの取得と配置は `scp` / `sftp` で足りる。
- Web UI を持つと、ブラウザ向けの HTTPS の証明書と、画面自体の認証が必要になる。SSH ならばどちらも要らない。
- 対象はネットワーク機器を操作するユーザであり、SSH の利用に支障がない。

**採用方針:**

- sshd だけを動かす小さなコンテナ（利用者作業用コンテナ）を追加する。
- イメージは Alpine Linux から自前でビルドする。  
  ユーザランドは busybox で足り、Perl や Python などのスクリプト言語は含めない。
- 認証は LDAP のパスワードで行う。ネットワーク機器へのログインと同じパスワードである。
- 詳細は 7 節に記載する。

### 3.6 chrony（時刻の配布）

ネットワーク機器に NTP で時刻を配る。ログの時刻と、機器のログの時刻を揃えるためである。  
Docker ホストの時刻の同期は、このサービスを使うかどうかにかかわらず前提とする（`make host_check` が確かめる）。

**方式:**

時計は Docker ホストとコンテナで共有している。コンテナは上流の NTP サーバを持たず、ホストの時計をそのまま配る（chrony の `local stratum 10`）。

| 案 | 内容 | 採らなかった理由 |
| --- | --- | --- |
| A | コンテナの chrony が上流に問い合わせて配る | 上流の NTP サーバに届く必要がある。ホストと二重に同期することになる |
| B | ホストを配れる NTP サーバ（chrony など）に替え、コンテナが中継する | ホストの `systemd-timesyncd` は配れない。ホストの手作業が増える |
| C | コンテナの chrony が、上流を持たずにホストの時計を配る | 採用 |

C の弱点は、ホストの同期が外れても、気づかずに配り続けることである。そのため、起動スクリプトがカーネルの時刻の状態を定期的に見て、外れていれば配るのを止める。

- 60 秒ごとに busybox の `adjtimex` で `maxerror`（カーネルが見積もる誤差の上限）を読む。Docker の既定の seccomp のままで読め、ケーパビリティも要らない。時計の変更はできない（コンテナに `CAP_SYS_TIME` は渡さず、chrony は `-x` で起動する）。
- `maxerror` は、ホストの NTP クライアントが同期するたびに小さく戻り、そのあいだは毎秒 500µs ずつ増える。`systemd-timesyncd` では、ほぼ 0 に戻るので、500 で割ると最後の同期からの秒数になる。
- しきい値は 3.6 秒（`timesyncd` で、最後の同期から 2 時間）とし、起動スクリプトの定数にする。`timesyncd` の問い合わせの間隔は最大で約 34 分なので、3回続けて失敗するまでは配り続ける。2時間のずれは、このホストの実測（約 5ppm）で 40ms 弱、カーネルの見積もり（500ppm）でも 3.6 秒で、ログの時刻としては使える。
- 超えたら `chronyc local off` で止め、下回ったら `chronyc local stratum 10` で戻す。止めているあいだも応答は返し、「同期していない」（Leap が Not synchronised、stratum 0）を伝える。機器はこれを採らないので、タイムアウトを待たずにもう片方のサーバ（冗長構成）へ移れる。止めたときと戻したときはログに出す。
- カーネル自身の「同期していない」の印（`timedatectl` の `System clock synchronized`）は、`maxerror` が 16 秒を超えるまで（約 9 時間）立たないので、判定には使わない。
- 起動したときの設定には `local` を書かない。最初の判定で同期を確かめてから配り始め、それまでは「同期していない」と答える。
- ホストの NTP クライアントが chronyd でも、同期のたびに `maxerror` を自分の誤差の見積もりに書き直し、外れれば書き直さなくなるので、同じ判定が効く見込みである（実機では確かめていない）。ただし、ホストがすでに時刻を配れる NTP サーバなら、このサービスは使わず、ホストに配らせるほうが素直である。サーバは上流との同期を自分で知っているので、この見張りが要らない。そのときの接続元の制限は、ホストの設定になる。

**採用方針:**

- 使うかどうかは選べるようにする。ホスト自身が時刻を配る構成などでは起動しない。`compose.yaml` で profile（`ntp`）に入れ、`.env` に `COMPOSE_PROFILES=ntp` と書いたときだけ起動する。既定は使わない（`.env.sample` ではコメントアウト）。更新しただけで新しいポートが開くことを避けるためである。止めたときの反映は `make down && make up`（`make up` だけでは、起動済みのコンテナが残る）。
- コンテナ名（`NTP_CONTAINER_NAME`）だけは、`compose.yaml` で既定の値（`chrony`）を持たせる。Compose は使わないサービスの値も検証するので、既定がないと、この変数を書いていない `.env` では、ほかのサービスも含めてすべてのコマンドが失敗する。
- イメージは Alpine Linux（`chrony` パッケージ）から自前でビルドする。ルートファイルシステムは読み取り専用とし、chrony は uid 100 に降格して動く。
- 123/udp を公開する。番号は機器が決めるので、変数にしない。
- 接続元は `DEVICE_NETWORKS` で制限する。本体に機能があるので（`allow`）、パケットフィルタではなく chrony の設定で絞る（8 節の「接続元の制限」）。範囲の外には応答しない。chrony は `allow` にホスト名を書くと名前を引いて受け入れるので、起動スクリプトが数字、`.`、`/` 以外を断る。書式の誤りは chrony 自身が断って止まる。
- busybox の `ntpd` は採らない。上流を持たないと、同期していないと答えるため。
- スモークテストは、配ること、範囲の外に答えないこと、しきい値を超えると「同期していない」と答えることを確かめる（5.6 節）。配っている最中に同期が外れて止まる流れ（`local off`）は確かめない。動いているコンテナのしきい値を変える仕組みが要り、テストのためだけの仕組みが増えるためである。判定の向きはテストで、`local off` が効くことは事前の検証で確かめた（ユーザーの判断）。
