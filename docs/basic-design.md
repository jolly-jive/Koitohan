# A little and kawaii network backend server `Koitohan` 基本設計書

## 1. 目的

Raspberry Pi 5 を Docker ホストとして利用し、  
**ネットワーク機器（Cisco / Aruba / Allied Telesis など）の管理基盤を統合的に提供するサーバ**を構築する。

提供機能と実装状況：

| 機能                 | コンポーネント | 状況                                           |
| -------------------- | -------------- | ---------------------------------------------- |
| ID管理（LDAP）       | OpenLDAP       | 実装済み                                       |
| 認証・認可（RADIUS） | FreeRADIUS     | 実装済み                                       |
| ログ管理（SYSLOG）   | syslog-ng      | 実装済み（ローテーションは 6.2 節）            |
| ファイル配布（TFTP） | tftpd-hpa      | 実装済み                                       |
| ユーザ管理           | スクリプト     | 実装済み（4.7 節）                             |
| ユーザの作業環境     | OpenSSH        | 実装済み（7 節）。公開鍵認証は保留（7.6 節）   |
| DHCP / DNS           | Kea / BIND9    | 未決定（11 節）                                |

本設計は「検証段階」を前提とし、可用性は後回しとするが、将来の冗長化を見据えた構成とする。

### 1.1 名称と目指す姿

「こいとはん」は大阪の土地言葉である。大阪の商家では、その家の娘を「いとはん」と呼ぶ。「いとしい人」あるいは「いとけない人」が元になったとされる言葉で、親にとっての大切な娘を指す。娘が二人以上いるとき、いちばん下の娘が「こ（小）いとはん」である。

大規模なネットワーク向けの高機能な管理サーバは、ほかに存在する。本プロダクトが目指すのは、そうした fat なサーバではない。

- Raspberry Pi で動くほど小さい。
- 最低限よりも少しましな管理機能を提供する。
- それでいて、可用性まで考慮する（冗長化は 12 節）。

小さくて愛しいサーバであることから、「こいとはん」と名付けた。機能を追加するときは、この規模感を保てるかどうかを判断基準とする。

### 1.2 用語

本プロダクトに関わる人を、次のように呼び分ける。

| 用語             | 意味                                                                 |
| ---------------- | -------------------------------------------------------------------- |
| こいとはん管理者 | Docker ホストにログインし、コンテナを操作できる人。                  |
| ユーザ           | `ou=People` にアカウントを持つ人。ネットワーク機器にログインする。   |
| ロール           | ユーザに割り当てる権限の区分（`admin` / `operator` / `readonly`）。 |

こいとはん管理者と、ロール `admin` のユーザは別である。ロール `admin` はネットワーク機器に対する管理者権限を表し、本プロダクト自体を管理する権限は含まない。単に「管理者」とは書かず、どちらを指すかを書き分ける。

## 2. 全体構成概要

```text
+-------------------------------------------+
|              Raspberry Pi 5               |
|               (Docker Host)               |
+-------------------------------------------+
| OpenLDAP     | Roles/Users   | 実装済み   |
| FreeRADIUS   | AuthZ/AuthN   | 実装済み   |
| syslog-ng    | Log Mgmt      | 実装済み   |
| tftpd-hpa    | TFTP          | 実装済み   |
| OpenSSH      | User Shell    | 実装済み   |
+-------------------------------------------+
| logrotate (Docker ホスト側)  | 実装済み   |
+-------------------------------------------+
```

通信経路：

```text
ネットワーク機器 --RADIUS 1812/udp--> FreeRADIUS --LDAPS 636/tcp--> OpenLDAP
ネットワーク機器 --SYSLOG 514/udp,tcp--> syslog-ng
ネットワーク機器 <--TFTP 69/udp--> tftpd-hpa
ユーザ --SSH 2222/tcp--> 利用者作業用コンテナ --LDAPS 636/tcp--> OpenLDAP
```

設定値（ドメイン、コンテナ名など）は `.env` に集約し、証明書・LDIF・FreeRADIUS の LDAP モジュール設定はスクリプトで `.env` から生成する。  
パスワードは人が決める値ではないので、`.env` には置かず、構築時に生成する（サービスアカウントは 4.10 節、OpenLDAP の管理者は 4.11 節）。

## 3. コンポーネント選定理由

### 3.1 OpenLDAP（ID管理）

**選定理由:**

- Raspberry Pi 5 でも軽量に動作する。
- Alpine のパッケージ（OpenLDAP 2.6。長期サポートのリリース）だけでイメージを組める。  
  当初は既製のイメージ（`osixia/openldap`）を使っていたが、中身が OpenLDAP 2.4 と Debian 10 のまま更新が止まっていたため、自前でビルドする形に改めた（8 節）。
- FreeRADIUS との連携が容易（`rlm_ldap`）。
- ロール管理を **memberOf（グループ）** で表現できる。
- 将来 Kerberos を導入する際にも自然に統合可能。
- 389 Directory Server は大規模・Red Hat 系向けで Pi には過剰。

**採用方針:**

- `ou=People` にユーザ。
- `ou=Roles` にロール（admin/operator/readonly）。
- 認証は当面 LDAP、将来 Kerberos へ拡張可能。
- 認可（権限）は RADIUS 側で決定。
- 待ち受けは LDAPS（636）のみとし、平文の 389 は待ち受けない（4.5 節）。

---

### 3.2 FreeRADIUS 4.x（認証・認可）

**選定理由:**

- LDAP の `memberOf` を参照してロール判定が可能。
- Cisco / Aruba / Allied などの VSA（Vendor-Specific Attribute）返却が容易。
- `unlang` で柔軟にポリシーを記述できる。
- Docker イメージが豊富で Pi 5 上でも十分軽量。
- 現時点で v4.x は、開発バージョンだが、複雑な機能を使う予定は無いため、正式リリースに先行して選定する。

**採用方針:**

- **機器種別 × ロール → 応答属性** を基本モデルとする（5 節）。
- 機器種別は、RADIUS クライアント定義（`clients.conf`）の `nas_type` で指定する。  
  Access-Request からは機器メーカーを確実には判定できないため、初版の「Vendor-ID による判定」から変更した。
- イメージ標準の設定をそのまま使い、Koitohan として書いた設定だけを読み取り専用で重ねる。

---

### 3.3 tftpd-hpa（TFTP）

**選定理由:**

- 軽量で Raspberry Pi に適する。
- ネットワーク機器のファームウェア配布やコンフィグ upload/download に適した実装。
- Alpine Linux のパッケージとして提供されており、小さなイメージ（約 9MB）を自前でビルドできる。  
  公式の Docker イメージは存在しないため、既存のイメージには依存しない。

**採用方針:**

- `/tftpboot` をホスト側ストレージに永続化。
- ファームウェア配布用ディレクトリ（`firmware/`）とコンフィグバックアップ用ディレクトリ（`configs/`）を階層分けする。
- `firmware/` は読み取り専用でマウントし、機器からの書き込み先を `configs/` に限定する。
- サーバは uid/gid 1000 で動作させ、ホスト側からそのままファイルを読み書きできるようにする。
- TFTP には認証がないため、書き込める容量を制限する（6.3 節）。
- 転送の記録（要求元とファイル名）をファイルに保存する（6.3 節）。
- PXE ブート環境は DHCP が前提となるため、11 節の判断に従う。

---

### 3.4 syslog-ng（ログ管理）

**選定理由:**

- ホスト別ログの分離が容易（フィルタ機能が強力）。
- ログローテーション・圧縮・長期保存の運用設計がしやすい。
- Docker イメージが安定しており、Pi 5 の NVMe と組み合わせて 3年保持が現実的。

**採用方針:**

- UDP/TCP 514 を開放し、ネットワーク機器からの SYSLOG を受信。
- ホスト名（または IP）ごとにログファイルを分割。
- 日次ローテーション＋圧縮＋3年間保持を基本ポリシーとする。
- ストレージは NVMe 256〜512GB を想定。

---

### 3.5 OpenSSH（ユーザの作業環境）

ユーザが、収集したログの閲覧と取得、TFTP のファイルの出し入れ、自身のパスワードの変更を行うための入口である。Web UI ではなく SSH とする。

**選定理由:**

- ログの取得前に `grep` / `sed` / `awk` などによる絞り込みを許したい。これはシェルそのものであり、Web で作り直すよりも、シェルを渡すほうが小さく済む。
- 「複数の機器の、特定の日付のログ」のような指定は、シェルの glob で書ける。
- ファイルの取得と配置は `scp` / `sftp` で足りる。
- Web UI を持つと、ブラウザ向けの HTTPS の証明書と、画面自体の認証が必要になる。SSH ならばどちらも要らない。
- 対象はネットワーク機器を操作するユーザであり、SSH の利用に支障がない。

**採用方針:**

- sshd だけを動かす小さなコンテナ（利用者作業用コンテナ）を追加する。
- イメージは Alpine Linux から自前でビルドする。  
  ユーザランドは busybox で足り、Perl や Python などのスクリプト言語は含めない。
- 認証は LDAP のパスワードで行う。ネットワーク機器へのログインと同じパスワードである。
- 詳細は 7 節に記載する。

## 4. LDAP ディレクトリ構造（基本設計）

```text
dc=example,dc=com
 ├── ou=People
 │     └── uid=alice
 ├── ou=Roles
 │     ├── cn=admin
 │     ├── cn=operator
 │     └── cn=readonly
 ├── ou=ServiceAccounts
 │     └── uid=radius
 └── ou=Policies
        ├── cn=default
        └── cn=serviceaccounts
```

サフィックスは `.env` の `LDAP_DOMAIN` から決まる（`example.com` → `dc=example,dc=com`）。  
`ou=People` は空の状態で構築し、ユーザは構築のあとで登録する（4.7 節）。`uid=alice` はその例である。検証用のテストアカウントは初期投入に含めず、スモークテストが自分のスタックの中に作る（5.6 節）。

### 4.1 ロール

ロールは `ou=Roles` 直下の `groupOfUniqueNames` で表現し、ユーザの所属は memberOf オーバーレイにより `memberOf` 属性として参照する。

```text
uid=alice
memberOf: cn=admin,ou=Roles,dc=example,dc=com
```

ロールはベンダーに依存しない。ベンダーごとの権限への読み替えは FreeRADIUS が行う（5 節）。

### 4.2 ServiceAccounts OU

サービスアカウント専用 OU を設け、  
アプリケーション・ミドルウェアが利用する認証情報を People OU と分離する。

### 4.3 ServiceAccounts OU の ACL 設計

ou=ServiceAccounts 以下のアカウントには、次の権限を付与する：

- dc=example,dc=com に対する read 権限
- ただし userPassword 属性は除外（先行する ACL により、本人・管理者以外は読み取り禁止）

これにより、FreeRADIUS はユーザ情報（uid、memberOf など）を参照できるが、
パスワード値そのものを読み取ることはできない。

### 4.4 FreeRADIUS 用サービスアカウント uid=radius

FreeRADIUS が LDAP に対して検索・bind を行うための専用アカウント。

- DN: uid=radius,ou=ServiceAccounts,dc=example,dc=com
- 認証方式: simple bind
- パスワード保存形式: SSHA
- パスワード: 構築時に生成する（4.10 節）
- 権限: 4.3 節のとおり

FreeRADIUS はこのアカウントを用いて：

- ユーザ DN の検索
- memberOf の取得

を行う。ユーザの認証は、検索で得た DN とユーザが入力したパスワードで bind して行う。

利用者作業用コンテナ（7 節）にも、同じ形のサービスアカウント `uid=openssh` を用意する。権限は同じく 4.3 節のとおりである。ユーザの一覧の取得と、認証のためのユーザ DN の検索に使う。

### 4.5 TLS

LDAP の通信はプライベート CA による TLS で保護する。

- プライベート CA を構築時に作成する。
- OpenLDAP にサーバ証明書を発行する（SAN はコンテナ名、FQDN、localhost）。
- FreeRADIUS と利用者作業用コンテナに、それぞれクライアント証明書を発行する。
- OpenLDAP は、接続してくる相手にクライアント証明書を要求する。
- 待ち受けは 636（LDAPS）と、コンテナ内の UNIX ソケット（`ldapi:///`）だけにする。389 は待ち受けない。  
  TLS は 1.3 に限る（`olcTLSProtocolMin: 3.4`）。つなぐのはこのスタックの FreeRADIUS と利用者作業用コンテナだけで、どちらも TLS 1.3 を使う。TLS 1.2 を残すと、前方秘匿性のない鍵交換（静的 RSA）も受け付けることになる。  
  DH パラメータのファイル（`olcTLSDHParamFile`）は置かない。これを使うのは TLS 1.2 の DHE の暗号スイートだけで、TLS 1.3 の鍵交換は名前付きのグループで決まる。  
  TLS の下限は、起動スクリプトが起動のたびに設定へ書く。`ldapi:///` から書き換えられても、次の起動で戻る。  
  加えて、TLS を使わない操作を拒否する設定（`olcSecurity: ssf=128`）を入れてある。待ち受けを誤って増やしても、平文では操作できない。  
  `ldapi:///` は対象外で、初期投入と保守に使える。
- 証明書と秘密鍵は、root だけが入れるディレクトリに読み取り専用でマウントし、起動時に `slapd` 専用のディレクトリ（tmpfs）へ写す。`slapd` は降格したあとで読むためである。Docker ホストのファイルの所有者は変えない。
- 証明書の名前はコンテナ名から決まるため、コンテナ名を変えたら証明書を作り直す。

証明書はこのスタックのコンテナ間でのみ使用し、外部には配布しない。そのため、再構築時は CA ごと作り直してよい。

鍵の扱いは次のとおりである。

- CA の秘密鍵は、証明書を発行したあとに消す。作り直しのたびに CA から作るので、発行のあとに使う場面がない。残しておくと、盗まれたときに、OpenLDAP が受け入れるクライアント証明書を作られる。証明書署名要求（CSR）も残さない。
- 鍵を置くディレクトリ（`CA/`）は、所有者しか入れないようにする（0700）。`make` と `make up` が設定する。パスワードを置く `secrets/` と、sshd のホスト鍵を置く `openssh/hostkeys/` も同じにする。
- FreeRADIUS のクライアント証明書の鍵だけは、ファイルのパーミッションを 0644 にしている。FreeRADIUS が、権限を落としたあと（コンテナ内の uid 101）で読むためである。Docker ホストのほかのユーザから読めないことは、ディレクトリのパーミッションで保っている。  
  ファイル単体のバインドマウントは、Docker ホスト側の親ディレクトリのパーミッションに左右されないので、コンテナからは読める。  
  所有者を uid 101 に変える方法は採らない。作り直しのたびに Docker ホストの root の権限が要るようになり、得られるものは変わらない。

### 4.6 初期投入

OU、ロール、サービスアカウント、ACL は LDIF として生成し、OpenLDAP の初回起動時（データベースが空のとき）に投入する。  
投入内容を変更して再投入するには、永続化したデータベースを削除する必要がある。

投入はイメージの起動スクリプト（`openldap/build/entrypoint.sh`）が行う。

- 設定（`cn=config`）とサフィックスのエントリは、スクリプトが作る。スキーマ、`memberOf` と参照整合性のオーバーレイ、TLS の設定はここに含まれる。
- 続いて、生成した LDIF をファイル名の順に入れる。このあいだ `slapd` は `ldapi:///` だけで待ち受けるので、投入の途中のディレクトリには外から届かない。
- 1つでも失敗したら、作りかけの設定とデータを消して終了する。欠けたディレクトリで待ち受けないためである。LDIF を直せば、次の起動でやり直せる。
- 最後まで済むと、設定のディレクトリに目印のファイル（`koitohan-seeded`）を置く。目印があれば、以降の起動では投入しない。
- 目印がないのに設定かデータが残っているとき（投入の途中で止められた、別のイメージが作った）は、起動しない。消すと中身が失われるので、スクリプトは消さず、こいとはん管理者に判断を委ねる。

4.7 節以降の項目には、スキーマ、オーバーレイ、サービスアカウントの追加を伴うものがある。  
これらは空のデータベースにしか投入されないため、稼働中の環境に対しては、データベースを消さずに適用する手順を別に用意する（パスワードポリシーの手順は 4.8 節）。

### 4.7 ユーザの管理

ユーザの登録・削除とロールの割り当ては、こいとはん管理者が Docker ホスト上のスクリプトで行う。管理用の画面は設けない。

- こいとはん管理者はホストのシェルを使えるため、画面がなくても作業できる。
- スクリプトは、本プロダクトのモデルに合わない登録を受け付けない。  
  汎用の LDAP 管理ツールでは、この制約を強制できない。
- ユーザに割り当てるロールは1つとする。スクリプトを通さずに複数のロールに所属させたユーザは、そのうちいちばん弱いロールとして扱われる（5.3 節）。
- 初期パスワードはこいとはん管理者が発行し、ユーザ本人が利用者作業用コンテナで変更する（7.5 節）。
- 発行するパスワードにも、4.8 節の規則を適用する。
- ユーザの登録、削除、ロールの変更のたびに、利用者作業用コンテナの `/etc/passwd` と `/etc/group` を作り直させる（7.2 節）。
- ユーザの削除とロールの変更では、そのユーザのログイン中のセッションを切る（7.2 節）。

提供する操作は、ユーザの登録、削除、ロールの変更、パスワードの再発行、ロックの解除とする。

**実装（`bin/manage_users.sh`）**

| 操作               | コマンド                        |
| ------------------ | ------------------------------- |
| 登録               | `add <ユーザ> <ロール> [<氏名>]` |
| 削除               | `delete <ユーザ>`               |
| ロールの変更       | `role <ユーザ> <ロール>`        |
| パスワードの再発行 | `passwd <ユーザ>`               |
| ロックの解除       | `unlock <ユーザ>`               |

- Docker ホストで実行し、作業はコンテナの中で行う。LDAP の操作は OpenLDAP のコンテナの `ldapi:///` から、パスワードの判定は利用者作業用コンテナの `pwqcheck` で行う。Docker ホストに追加で要るものはない。
- 登録で受け付けないもの: ログイン名として使えない名前（`koitohan-update-users` と同じ規則。7.9 節）、すでにあるユーザ、利用者作業用コンテナのイメージに元からあるアカウントと同じ名前、3つのロール以外のロール。
- パスワードは端末から2回尋ねる。端末がないときは、標準入力の1行目を読む。引数では受け取らない（`ps` で見えるため）。
- `pwqcheck` には、ユーザ名と氏名も渡す。これらをもとにしたパスワードは拒否される。
- パスワードは、パスワード変更の拡張操作（`ldappasswd`）で、平文のまま標準入力から渡す。ハッシュ化は OpenLDAP が行う。エントリの追加に `userPassword` を含めないのは、ppolicy をまだ適用していないデータベース（4.8 節）では、平文で書いた値がそのまま保存されるためである。
- 登録は、エントリの追加、パスワードの設定、ロールへの追加の順に行う。途中で失敗したときは、エントリを削除する。割り当てた `uidNumber` は戻さない（4.9 節）。
- ロールの変更は、新しいロールへの追加、元のロールからの削除の順に行う。途中で失敗しても、ロールのないユーザにはならない。複数のロールに所属しているユーザ（スクリプトを通さずに作られたもの）も、指定したロール1つにまとめる。
- ロックの解除は、`pwdAccountLockedTime` と `pwdFailureTime` を削除する。失敗の記録も消すのは、残しておくと、次の1回の失敗でふたたびロックされるためである。`pwdFailureTime` は通常の変更を受け付けないので、relax 制御を付ける。
- 削除、ロールの変更、パスワードの再発行、ロックの解除は、スクリプトを通さずに作られたユーザも対象にできる。
- スモークテスト（`make test`）で、すべての操作と、受け付けない登録を確かめる。

### 4.8 パスワードポリシー

実装済みである。複雑さは、利用者作業用コンテナの `passwd` と 4.7 節のスクリプトが判定する（`.env` の `PASSWDQC_MIN`）。最小の長さとロックは、OpenLDAP の ppolicy オーバーレイが強制する（`.env` の `PPOLICY_*`）。

**複雑さ**

文字の種類を一律に強制することはしない。短いパスワードにだけ文字の種類を求め、長ければ種類を問わない。

| 含む文字の種類 | 最小の長さ |
| -------------- | ---------- |
| 3種類以上      | 8          |
| 2種類          | 10         |
| 1種類          | 12         |

文字の種類は、大文字・小文字・数字・その他の4つである。値は既定値であり、`.env` で変更できるようにする。

判定には passwdqc を使う。上の表は `min=12,10,10,8,8` にあたる。  
passwdqc は、先頭の大文字と末尾の数字を種類に数えない。たとえば `Password1` は1種類として扱われる。ありがちな水増しを防ぐための仕様であり、表を素朴に読んだ場合よりも厳しくなる。

passwdqc は Alpine のパッケージとしては入手できないので、利用者作業用コンテナのイメージのビルドの中で、ソースからビルドする。バージョン（2.1.0）とチェックサムは Dockerfile で固定する。  
4.7 節のスクリプトも、このコンテナの中の `pwqcheck` を呼んで判定する。Docker ホストには入れない。判定の設定を1か所にするためである。

**強制する場所**

| 場所                                           | 強制する内容                   |
| ---------------------------------------------- | ------------------------------ |
| パスワードを設定する入口（4.7 節、7.5 節）     | 上の表のすべて                 |
| OpenLDAP（ppolicy オーバーレイ）               | 最小の長さ（8 文字）とロック   |

表のとおりの判定を OpenLDAP 自身に行わせるには、判定用のモジュールを組み込んだイメージを自前でビルドする必要があり、本プロダクトの規模に合わないため採用しない。

そのため、利用者作業用コンテナのシェルを使えるユーザは、入口の判定を通さずに自身のパスワードを書き換えることができる。その場合でも、OpenLDAP が保証する最小の長さは守られる。  
この規則の目的は、不注意で弱いパスワードを設定することを防ぐことにあり、意図して迂回するユーザまでは対象としない。この制約は README の既知の問題にも記載する。

**ロック**

認証に続けて失敗したアカウントを、一定時間ロックする。

| 項目               | 既定値 | `.env` の変数（時間は秒で指定） |
| ------------------ | ------ | ------------------------------- |
| 失敗の回数         | 10 回  | `PPOLICY_MAX_FAILURE`           |
| 失敗を数える期間   | 5 分   | `PPOLICY_FAILURE_WINDOW`        |
| ロックする時間     | 5 分   | `PPOLICY_LOCKOUT_DURATION`      |

値は `.env` で変更できる。OpenLDAP が保証する最小の長さも同様である（`PPOLICY_MIN_LENGTH`）。

- FreeRADIUS も利用者作業用コンテナも LDAP の bind で認証するため、失敗の回数は両者で共通に数えられる。
- ロックは時間の経過で解除される。こいとはん管理者がスクリプトで解除することもできる（4.7 節）。
- `ou=ServiceAccounts` のアカウントはロックの対象から外す。  
  FreeRADIUS のサービスアカウントがロックされると、すべてのユーザの認証が止まるためである。

ネットワーク機器のログイン画面に到達できる相手は、誤ったパスワードを送り続けることで、任意のユーザをロックできる。ロックを時間で解除するのは、この影響を一時的なものに留めるためである。

**実装（`openldap/ldif/400-PPolicy.ldif`）**

- `scripts/generate_ldap_base.sh` が `.env` から生成し、初期投入（4.6 節）に含める。番号は、サービスアカウントの LDIF（`300`）のあと、ACL（`900`）の前になるように付けた。順序の理由は 7.7 節のとおりである。
- ファイルの中は、モジュールの読み込み、オーバーレイの追加、ポリシーのエントリ、サービスアカウントへの割り当ての順である。
- ポリシーは `ou=Policies` に2つ置く。
  - `cn=default`: オーバーレイの既定のポリシー（`olcPPolicyDefault`）。割り当てのないエントリすべてに効く。最小の長さとロックを持つ。
  - `cn=serviceaccounts`: ロックを無効にしたポリシー。`ou=ServiceAccounts` の各アカウントに `pwdPolicySubentry` で割り当てる。
- `pwdCheckQuality` は `2` にする。ハッシュ済みの値は長さを確かめられないので、拒否する（7.7 節）。  
  このため、適用のあとは、ハッシュ済みのパスワードを持つエントリを追加できない。サービスアカウントを増やすときは、その LDIF を先に適用してから、このファイルを適用し直す。
- 平文で書き込まれた値は OpenLDAP がハッシュ化する（`olcPPolicyHashCleartext`）。ロックされていることは相手に伝えない（`olcPPolicyUseLockout: FALSE`）。
- 稼働中のデータベースには、コンテナ内の `ldapi:///` から同じファイルを適用する。データベースを消す必要はない。
- 適用し直せるように、ポリシーの値とサービスアカウントへの割り当ては、エントリの追加とは別の、置き換えの変更として書いてある。`.env` の値を変えたときは、LDIF を生成し直して `ldapmodify -c` で適用する。すでにあるモジュール、オーバーレイ、エントリの追加はエラーになるが、`-c` で先へ進み、値だけが置き換わる。
- スモークテスト（`make test`）で、次を確かめる。
  - 最小の長さに満たないパスワードと、ハッシュ済みの値を、ユーザ本人が OpenLDAP に直接書き込もうとして拒否されること。
  - RADIUS で失敗を重ねたユーザが、正しいパスワードでも、RADIUS と SSH の両方で拒否されること。スクリプトでロックを解除すると、両方で通ること。
  - 同じ回数だけ bind に失敗させたサービスアカウントが、ロックされないこと。FreeRADIUS も `nslcd` も接続を保ったままにするので、ログインの成否ではなく、エントリの `pwdAccountLockedTime` を見る。
  - 利用者作業用コンテナの `passwd` と 4.7 節のスクリプトが、ppolicy を有効にした OpenLDAP に対して働くこと（従来の確認が、そのままこれにあたる）。

### 4.9 posixAccount

利用者作業用コンテナも、番号を割り当てるスクリプト（4.7 節）も、この節の属性を前提として実装済みである。

`ou=People` のユーザに、`inetOrgPerson` に加えて `posixAccount` を持たせる。

利用者作業用コンテナでは、ユーザが書き込んだファイルが、UID の数値のまま Docker ホストのディスクに残る。番号を LDAP で管理することで、コンテナを作り直してもファイルの所有者が変わらない。

| 属性            | 値                                     |
| --------------- | -------------------------------------- |
| `uidNumber`     | 10000〜59999 から、登録順に割り当てる  |
| `gidNumber`     | 10000（全ユーザ共通のグループ）        |
| `homeDirectory` | `/home/<uid>`                          |
| `loginShell`    | `/bin/sh`                              |

- 10000 から始めるのは、Docker ホストとコンテナが使う番号を避けるためである。  
  システムのアカウント（999 以下。FreeRADIUS の 101、OpenLDAP の 100 を含む）、ホストの一般ユーザ（1000 以降）、systemd が使う範囲（60001 以降）、ユーザ名前空間の subuid（100000 以降）のいずれとも重ならない。
- 番号は再利用しない。削除したユーザのファイルは数値のまま残るので、同じ番号を別のユーザに割り当てると、そのファイルが新しいユーザのものになる。
- そのため、次に割り当てる番号は LDAP に記録する。「使用中の最大値 + 1」では、最後に登録したユーザを削除したときに再利用が起きる。
- 番号の割り当ては 4.7 節のスクリプトが行う。
  - 次に割り当てる番号は、サフィックスの直下のエントリ `cn=nextUidNumber` の `serialNumber` に置く。`objectClass` は `device` である。OpenLDAP の標準のスキーマだけで作れるものを選んだ。
  - 割り当ては、読んだ値の削除と、次の値の追加を、1回の変更で行う。同時に実行された別の割り当てが同じ番号を取っていれば、削除が失敗するので、読み直してやり直す。
  - このエントリは初期投入に含めず、最初の登録のときにスクリプトが作る。初期値は、その時点で使われている最大の番号の次（ユーザがいなければ 10000）である。稼働中の環境にも、そのまま導入できる。  
    スクリプトを使い始める前に削除されたユーザの番号までは分からない。その範囲では、再利用が起こりうる。

ロールは `groupOfUniqueNames` のままとし、`posixGroup` にはしない。OS のグループへの対応づけは、利用者作業用コンテナの中で行う（7.2 節）。

`posixAccount` を持たせておくと、ほかの Linux ホストなどの認証にも同じディレクトリを使える余地がある。これを提供するかどうかは未決定である（12 節）。

### 4.10 サービスアカウントのパスワード

実装済みである。サービスアカウント（4.4 節）のパスワードは、構築時にスクリプトが生成する。

人が決める値にすると、サンプルの値や弱いパスワードのまま運用されうる。また、このパスワードを使うのはコンテナだけで、通常の運用では人が入力する場面がない。そこで、設定値ではなく、証明書や sshd のホスト鍵と同じ生成物として扱う。

**置き場所と参照**

- Docker ホストの `secrets/` に、アカウントごとに1ファイルで置く（`freeradius_service_account_password`、`openssh_service_account_password`）。パーミッションは 0600 で、git の管理対象外である。
- こいとはん管理者は、このファイルを読んで値を確かめる。表示のためのコマンドは設けない。  
  調査のためにサービスアカウントで bind するときも、ファイルのまま渡せる（`ldapsearch -y`）ので、値を画面に出す必要はほとんどない。
- ファイルの末尾に改行を付けない。`ldapsearch -y` も `ldappasswd -T` も、改行をパスワードの一部として扱う。

**生成（`make secrets`）**

- `scripts/generate_service_account_password.sh` が、48 桁の 16 進数（192 ビット）を `openssl rand` で作る。  
  値は FreeRADIUS の LDAP モジュール設定の引用符の中と、`nslcd.conf` の行に、そのまま書き込まれる。記号を含めないのは、そこでのエスケープを不要にするためである。
- すでにあるファイルは作り直さない。`make clean` でも消さない。  
  初期投入（4.6 節）は空のデータベースにしか入らないので、作り直すと、ディレクトリが知っているパスワードと食い違い、すべてのユーザの認証が止まる。

**渡し方**

| 渡す先                               | 方法                                                                 |
| ------------------------------------ | -------------------------------------------------------------------- |
| OpenLDAP（初期投入の LDIF）          | `scripts/generate_ldap_base.sh` がファイルを読み、ハッシュ化して書く |
| FreeRADIUS（LDAP モジュール設定）    | `scripts/generate_freeradius_ldap.sh` がファイルを読んで書く         |
| 利用者作業用コンテナ                 | ファイルを読み取り専用でマウントする（root しか入れないディレクトリ）|

利用者作業用コンテナには、以前は環境変数で渡していた。環境変数は `docker inspect` に表示され、コンテナ内でも root のプロセスの環境として残るので、ファイルに改めた。コンテナには自分のアカウントのファイルだけを見せ、FreeRADIUS のものは見せない。

**変更**

実装済みである。稼働中の環境でパスワードを変えるには、Docker ホストで `bin/change_service_account_password.sh` を、アカウントごとに実行する（引数は `freeradius` か `openssh`）。スクリプトは次の順に進める。

1. 新しいパスワードを生成し、仮のファイル（`secrets/` の中）に置く。生成には `make secrets` と同じスクリプトを使う。
2. OpenLDAP のコンテナ内の `ldapi:///` から、`ldappasswd` でディレクトリに書き込む。  
   平文で渡す。ppolicy がハッシュ済みの値を拒否するためである（4.8 節）。
3. 仮のファイルを本来の名前に移し、そのパスワードで bind できることを確かめる。
4. パスワードを含む生成物（初期投入の LDIF、FreeRADIUS の LDAP モジュール設定）を生成し直す。
5. そのアカウントを使うコンテナを作り直す。  
   再起動では足りない。利用者作業用コンテナはファイル単体をマウントしているので、古いファイルを見たままになる。作り直すと、ログイン中のセッションは切れる。

- 2 が失敗したときは、何も変わっていない。3 以降で止まったときは、もう一度実行すればよい。  
  ディレクトリへの書き込みは、コンテナの root（ディレクトリの管理者）として行うので、いまのパスワードを必要としない。したがって、`secrets/` とディレクトリが食い違った状態からも、同じ操作で戻せる。
- 実行の前に、対象のコンテナが、これから書き換えるファイルをマウントしていることを確かめる。  
  対象のスタックは `COMPOSE_PROJECT_NAME` と `COMPOSE_FILE` で変えられるが（4.7 節）、生成物の場所は別に決まる（`KOITOHAN_GENERATED_ROOT`。指定しなければリポジトリの直下）。テスト用のスタックのディレクトリを書き換えながら、稼働中のスタックの `secrets/` を差し替えてしまうと、次に稼働中のコンテナを作り直したときに全員の認証が止まる。これを防ぐための確認である。

スモークテストは、稼働中のスタックの `secrets/` を使わない。テストのたびに、パスワードと、それを含む生成物を `tests/generated/` に作る（5.6 節）。これにより、テスト用のスタックでパスワードの変更を確かめられる。

### 4.11 OpenLDAP の管理者のパスワード

実装済みである。OpenLDAP には、パスワードで bind する管理者が2つある。データの管理者（`cn=admin,<サフィックス>`）と、設定の管理者（`cn=admin,cn=config`）で、どちらも rootdn なので、ACL と ppolicy の判定を受けない。このパスワードも、サービスアカウントと同じく、構築時にスクリプトが生成する。

以前は `.env` に置いていた（`LDAP_ADMIN_PASSWORD`、`LDAP_CONFIG_PASSWORD`）。人が使う場面があると考えたためだが、次の理由で改めた。

- 実際には、使う場面がほとんどない。このスタックのスクリプトは、コンテナ内の `ldapi:///`（コンテナの root が、パスワードなしで管理者になる）だけを使う。
- 人が決める値にすると、サンプルの値のまま運用されうる。  
  OpenLDAP はクライアント証明書を要求するが（4.5 節）、証明書を持つのは FreeRADIUS と利用者作業用コンテナである。パスワードが推測できると、このどちらかを奪われた時点で、管理者の権限まで渡る。推測できなければ、奪われるのはサービスアカウントの読み取り権限にとどまる。
- 環境変数で渡すと、`docker inspect` に表示される。当時のイメージ（`osixia/openldap`）では、コンテナ内にも、だれでも読めるファイルとして残った。

**置き場所と渡し方**

- Docker ホストの `secrets/` に置く（`ldap_admin_password`、`ldap_config_password`）。形式、パーミッション、生成の方法は、サービスアカウントのもの（4.10 節）と同じである。生成するスクリプトは `scripts/generate_ldap_admin_password.sh`。
- OpenLDAP のコンテナには、ファイルを読み取り専用でマウントする（`/etc/koitohan/secrets/`。root しか入れない）。
- 起動スクリプトは、読んだ値をログに出さない。スモークテストが、ログにパスワードが出ていないことを確かめる。

**起動のたびの再設定**

起動スクリプトは、起動のたびに、渡されたパスワードをハッシュ化して設定に書き込む（`slapd` を起動する前に、`slapmodify` で `olcRootPW` を置き換える）。したがって、ディレクトリの側だけを書き換えても、次の起動で元に戻る。パスワードの正は、つねに `secrets/` のファイルである。

この動作により、変更と移行は、ファイルを替えてコンテナを作り直すだけで済む。

**変更**

稼働中の環境でパスワードを変えるには、Docker ホストで `bin/change_ldap_admin_password.sh` を実行する。2つを同時に変える。

1. 新しいパスワードを2つ生成し、仮のファイルに置く。
2. 仮のファイルを本来の名前に移す。
3. OpenLDAP のコンテナを作り直す。イメージが、起動のときに新しいパスワードを設定する。  
   再起動では足りない。ファイル単体をマウントしているので、古いファイルを見たままになる。
4. 新しいパスワードで bind できることを確かめる。

- 2つを同時に変えるのは、OpenLDAP の作り直しを1回にするためである。作り直しのあいだは、すべてのユーザの認証が止まる。
- いまのパスワードを必要としないので、途中で止まったときは、もう一度実行すればよい。
- 実行の前に、対象のコンテナが、これから書き換えるファイルをマウントしていることを確かめる（4.10 節と同じ理由による）。
- OpenLDAP が再起動すると、FreeRADIUS はしばらく認証を拒否する（未解決の不具合）。スクリプトのあとで FreeRADIUS を再起動する手順を、運用ガイド（`docs/configuration.md`）に書いている。

## 5. FreeRADIUS ポリシー（基本設計）

FreeRADIUS 4.x は構成ファイルの構造が 3.x と異なるため、設定は 4.x の公式ドキュメントに基づいて作成する。

### 5.1 認証の流れ

仮想サーバ `ldap-pap` が 1812/udp で Access-Request を受け付ける。

1. サービスアカウントで LDAP を検索し、ユーザの DN と `memberOf` を取得する。
2. ユーザがどのロールにも所属していなければ、ここで拒否する（ポリシー `authz_vendor_role`）。
3. `clients.conf` の `nas_type` と、ユーザのロールから、応答属性を決定する（同じポリシー）。
4. ユーザの DN と入力されたパスワードで LDAP に bind し、成功すれば認証成功とする。

パスワードは PAP で受け取る。LDAP 側のハッシュを FreeRADIUS が読み取る方式は採らない。

受け付ける送信元は、機器のネットワーク（`.env` の `DEVICE_NETWORKS`。8 節の「接続元の制限」）とループバックに限定する。  
そのうえで、`clients.conf` に登録された機器だけが共有シークレットで認証される。

### 5.2 機器種別（nas_type）

`nas_type` は大文字小文字を区別せず、前方一致で機器種別に正規化する。

| 機器種別     | `nas_type` の値           | 返す属性                     |
| ------------ | ------------------------- | ---------------------------- |
| Cisco        | `cisco`                   | `Cisco-AVPair`               |
| ArubaCX      | `aruba-cx`                | `Aruba-Priv-Admin-User`      |
| ArubaAP      | `aruba-ap`                | なし                         |
| Fortinet     | `fortinet`、`fortigate`   | `Fortinet-Group-Name`        |
| Juniper      | `juniper`                 | `Juniper-Local-User-Name`    |
| PaloAlto     | `palo-alto`               | `PaloAlto-Admin-Role`        |
| Service-Type | `service-type`、`rfc2865` | `Service-Type`               |
| IETF-MPL     | `ietf-mpl`、`allied`      | `Management-Privilege-Level` |
| Nothing      | `nothing`、`no`、`none`   | なし                         |

上記のどれにも当てはまらない値は IETF-MPL として扱い、`Reply-Message` で不明な `nas_type` であることを通知する。

### 5.3 ロールと応答属性の対応

| 機器種別     | admin                 | operator           | readonly           |
| ------------ | --------------------- | ------------------ | ------------------ |
| Cisco        | `shell:priv-lvl=15`   | `shell:priv-lvl=7` | `shell:priv-lvl=1` |
| ArubaCX      | 15                    | 7                  | 1                  |
| ArubaAP      | 許可（属性なし）      | 拒否               | 拒否               |
| Fortinet     | `super_admin`         | `readonly`         | `readonly`         |
| Juniper      | `superuser`           | `operator`         | `read-only`        |
| PaloAlto     | `superuser`           | `readonly`         | `readonly`         |
| Service-Type | `Administrative-User` | `NAS-Prompt-User`  | `Login-User`       |
| IETF-MPL     | 15                    | 7                  | 1                  |
| Nothing      | 許可（属性なし）      | 許可（属性なし）   | 許可（属性なし）   |

Fortinet、Juniper、Palo Alto の値は機器側に定義されたプロファイル名・ユーザ名であり、機器側の設定と一致させる必要がある。

複数のロールに所属しているユーザは、そのうちいちばん弱いロールとして扱う。優先順位は `readonly`、`operator`、`admin` の順で、たとえば `readonly` と `admin` の両方に所属していれば `readonly` になる。

- 権限に関わる判定なので、迷う余地があるときは弱い側に倒す。強いロールを意図せず残したまま弱いロールを足しても、強い権限は効かない。
- `memberOf` の値の並び順には左右されない。そのために、LDAP モジュールは `memberOf` の値をすべて取り込む（`control.LDAP-Group += 'memberOf'`。`:=` では最初の値しか残らない）。
- 利用者作業用コンテナも同じ順で決める（7.2 節）。
- 4.7 節のスクリプトはロールを1つしか割り当てないので、この状態は、スクリプトを通さずにディレクトリを書き換えたときにだけ生じる。スクリプトの「ロールの変更」で1つにまとめられる。

3つのロール以外のグループ（`ou=Roles` 直下にないもの、未定義のロール）は、何の権限も与えない。3つのロールのどれかにも所属していれば、そのロールが効き、ほかの所属は無視する。

どのロールにも所属していないユーザは、ほかのグループに所属していても、機器種別にかかわらず拒否する。そのようなユーザは 4.7 節のスクリプトからは生まれず、本プロダクトのモデルにない状態だからである。以前は、ロール以外のグループにだけ所属しているユーザを `Management-Privilege-Level = 1` で許可していたが、機器種別を見ないので、`readonly` では拒否する Aruba の AP にも入れてしまっていた。権限に関わるので弱い側に倒し、拒否に揃えた。

- 拒否は bind の前に行う。パスワードは確かめず、ppolicy の失敗の回数（4.8 節）にも数えない。
- 応答に理由（`Reply-Message`）は付けない。機器の側からは、存在しないユーザやパスワードの誤りと区別がつかない。
- 理由は、FreeRADIUS をデバッグモードで起動したときの出力にだけ現れる（`no role for '<ユーザ名>'`。ロール以外のグループに所属していれば、`unknown role: <名前>` か `invalid role: <DN>` を添える）。通常の運用では `radius.log` に残らない。

### 5.4 ベンダーの追加

新しいベンダーに対応するときは、次の4か所を揃える。

- 辞書（`Koitohan.dict`）の機器種別
- `nas_type` の正規化ルール
- 各ロールの応答属性
- スモークテスト（`tests/`）のクライアントと期待値

### 5.5 設定ファイルの区分

| 区分     | ファイル                                               | 扱い                                |
| -------- | ------------------------------------------------------ | ----------------------------------- |
| 共通     | 辞書、ポリシー、仮想サーバ、有効化するモジュールの一覧、detail ログのモジュール設定（6.2 節） | リポジトリで管理する |
| 環境ごと | `clients.conf`                                         | 利用者が書く。サンプルのみ管理する  |
| 生成     | LDAP モジュール設定                                    | `.env` から生成する。直接編集しない |

### 5.6 スモークテスト

`make test` は、すべてのコンテナを稼働中のスタックとは別のプロジェクトとして起動し、認証から応答属性までを通しで確かめる。  
空のディレクトリで起動し、テストアカウント（`admin01` / `operator01` / `readonly01`）を `bin/manage_users.sh` で登録してから、機器種別とロールの組み合わせごとに応答を照合する。  
ロールのないユーザ（`norole01`）はスクリプトでは作れないので（4.7 節）、テストが `ldapi:///` から直接作り、拒否されることの確認に使う。これをスクリプトより先に作ることで、番号の割り当てが、すでにあるユーザの次から始まることも確かめている。  
複数のロールに所属するユーザも同じくスクリプトでは作れないので、テストが `ldapi:///` からロールを足し、いちばん弱いロールが効くこと（5.3 節）を、RADIUS と SSH の両方で確かめる。`operator` のユーザに `admin`、`readonly` の順で足すので、`memberOf` の最初の値だけを見ても、いちばん強いロールを採っても、期待と合わない。  
FreeRADIUS のイメージや設定を変更したときは、反映の前に実行する。

テストは `compose.yaml` をそのまま読み、ポート、永続データ、`clients.conf`、パスワードを含む生成物だけを `tests/compose.test.yaml` で差し替える。イメージとその他のマウントは本番と同じものを使う。  
サービスアカウントと OpenLDAP の管理者のパスワード、初期投入の LDIF、LDAP モジュール設定は、テストが `make` と同じスクリプトで `tests/generated/` に作る（4.10 節、4.11 節）。稼働中のスタックのものは読まず、書き換えもしない。  
要求は FreeRADIUS のコンテナ内から送り、送信元アドレス（`127.0.0.N`）で機器種別を切り替える。

応答の照合のあと、detail ログを別の名前に移してからもう一度認証し、FreeRADIUS が同じ名前でファイルを作り直すことを確かめる。ログローテーション（6.2 節）が頼っている動作であり、イメージを更新したときの退行を検出する。

続いて、Docker ホストから OpenLDAP のコンテナへ、FreeRADIUS のクライアント証明書で TLS のハンドシェイクを送り、TLS 1.3 は成立し、TLS 1.2 は断られることを確かめる（4.5 節）。

最後に、`bin/backup.sh` でバックアップを取り、そのあとでユーザーを1人消してから、OpenLDAP のコンテナを匿名ボリュームごと消して、`bin/restore_ldap.sh` で復元する（8 節の「バックアップと復元」）。消したユーザーが戻って RADIUS で認証できること、バックアップの前に変えたパスワードで SSH にログインできること、次の `uidNumber` が続きから割り当てられること、初期投入が走っていないこと、`configs/` のファイルが所有者ごと戻ることを確かめる。

### 5.7 アカウンティング

RADIUS アカウンティングは提供しない。1813/udp も公開しない。

このスタックの RADIUS は、機器へのログインの認証にだけ使う。この用途では、アカウンティングで得られる情報がほかの記録と重なる。

- 誰が、いつ、どの機器にログインしたかは、認証の detail ログ（`auth-detail`、`reply-detail`）に残る。
- ログアウトと操作の内容は、機器が syslog で送る（6.1 節）。  
  RADIUS のアカウンティングが記録するのはセッションの開始と終了であり、コマンド単位の記録は持たない。

接続時間や通信量を課金や監査に使う用途（ISP、802.1X）は、対象としていない。

## 6. ログポリシー（基本設計）

### 6.1 syslog-ng

ネットワーク機器からのログは、

```
/var/log/Hosts/<host>/<host>.log
```

に置く（ホスト側では `syslog-ng/log/Hosts/<host>/<host>.log`）。

日次ローテーション×3年間の場合、一つのネットワーク機器に対して、約1100ファイルが作成されることになる。複数のネットワーク機器のログファイルを一つのディレクトリに保存すると、数万のファイルを一つのディレクトリに置くことになる可能性がある。この場合、

- `ls` が遅い
- `rm` が遅い
- logrotate の glob が重くなる
- 運用上の視認性が悪い

という問題が出る。

これらの問題を避けるため、ネットワーク機器毎にディレクトリを分けるものとする。

ログファイルの所有者は、コンテナの実行ユーザ（uid/gid 1000）とする。

**syslog-ng の設定**

```
destination d_host_logs {
    file("/var/log/Hosts/${HOST}/${HOST}.log"
         create-dirs(yes)
         owner(1000)
         group(1000)
         perm(0644));
};
```

コンテナ内では 1514（udp/tcp）で待ち受け、ホストの 514 として公開する。  
機器のネットワーク（`.env` の `DEVICE_NETWORKS`。8 節の「接続元の制限」）の外から届いたメッセージは、フィルタで捨てる。認証がなく、送信元ごとにディレクトリを作るので、制限しないとディスクを埋められる。  
送信元が名乗るホスト名をそのまま `${HOST}` として使う（`keep-hostname(yes)`）。

**デバッグログ**

検証段階では、受信した生メッセージとホスト系マクロを `/var/log/debug.log` にも記録する。  
全機器のログが1ファイルに集まり続けるため、6.2 節のローテーションの対象とし、7 日分だけを残す。出力を止めるかどうかは、検証完了時に判断する。

### 6.2 ログローテーション

ログのローテーションは、Docker ホスト側の logrotate で行う。

- Dockerコンテナには、cron/systemd が組み込まれていない事が多い。
- コンテナを軽量化できる
- コンテナの再起動や再デプロイに影響されない
- ホスト側の cron/systemd-timer が使える

設定は `scripts/generate_logrotate.sh` が `logrotate/koitohan` に生成する（`make logrotate_conf`）。リポジトリの絶対パスと、syslog-ng のコンテナ名（`.env` の `SYSLOG_CONTAINER_NAME`）が入るためである。  
`/etc/logrotate.d/` への配置は `sudo` が要る作業であり、`make` には含めず、運用ガイド（`docs/logs.md`）に手順を記載する。logrotate は root の所有でない設定を読まないので、シンボリックリンクではなく複製を置く。生成し直したときは、置き直す。

**対象**

| ファイル                                                       | 書き込むプロセス       | 切り替えの方法                               | 保持    |
| -------------------------------------------------------------- | ---------------------- | -------------------------------------------- | ------- |
| `syslog-ng/log/Hosts/<host>/<host>.log`                        | syslog-ng（uid 1000）  | 名前を変え、syslog-ng に再オープンを指示する | 1096 日 |
| `syslog-ng/log/debug.log`                                      | 同上                   | 同上                                         | 7 日    |
| `freeradius/log/radius.log`                                    | FreeRADIUS（uid 101）  | 複製して、元のファイルを空にする             | 1096 日 |
| `freeradius/log/radacct/<client>/auth-detail`、`reply-detail`  | 同上                   | 名前を変える                                 | 1096 日 |
| `tftpd-hpa/log/tftpd.log`                                      | `syslogd`（root）      | 名前を変える                                 | 1096 日 |

1096 日は3年分にあたる。保持の日数は、生成スクリプトの先頭に定数として置いている。

**共通の方針**

- 日次で切り替える。切り替えたあとのファイルは `<元の名前>-YYYY-MM-DD` とし、元と同じディレクトリに置く。
- 日付は、ファイルの中身の日とする（`dateyesterday`）。logrotate は日付が変わった直後に動くので（Raspberry Pi OS では systemd のタイマーで 0 時台）、指定しないと、中身の翌日の日付が付く。
- gzip で圧縮する。ただし、直前の1日分は圧縮しない（`delaycompress`）。切り替えの直後に届く書き込みを受けるためであり、前日のログをそのまま `grep` できる利点もある。
- 空のファイルは切り替えない（`notifempty`）。ログを送らなかった日のファイルは作られない。
- ログの所有者は root ではないので、`su` でコンテナの実行ユーザに切り替えて操作する。Docker ホストにその名前のユーザがあるとは限らないため、数値で指定する。圧縮したファイルも元と同じ所有者とパーミッションになるので、機器のログは、圧縮後も利用者作業用コンテナから読める（7 節）。`postrotate` のスクリプトは root で動く。
- logrotate は、初めて見たファイルについては状態を記録するだけで、切り替えは翌日から始める。

**syslog-ng**

syslog-ng はログファイルを開いたまま書き込むため、ローテーション後にファイルの再オープンを指示する。再オープン時に syslog-ng が新しいファイルを作成するので、logrotate 側では作成しない。

```
"/srv/docker/syslog-ng/log/Hosts/*/*.log" {
    su 1000 1000
    daily
    dateext
    dateyesterday
    dateformat -%Y-%m-%d
    rotate 1096
    compress
    delaycompress
    missingok
    notifempty
    nocreate
    sharedscripts
    postrotate
        docker exec syslog-ng syslog-ng-ctl reopen --control=/config/syslog-ng.ctl > /dev/null
    endscript
}
```

syslog-ng のコンテナが止まっているあいだはログが増えないので、切り替えも再オープンも起きない。

**FreeRADIUS**

- `radius.log` は、FreeRADIUS が追記モードで開いたままにする。イメージに付属する logrotate の設定が `copytruncate` を使っており、それに倣った。複製してから空にするまでのあいだに書かれた行は、失われることがある。
- detail ログ（認証の要求と応答の記録）は、イメージの既定では FreeRADIUS が日付入りの名前（`auth-detail-2026-10-8` など）で日ごとに分ける。ただし、圧縮も削除もされない。そこで、モジュール設定（`mods-available/detail.log`）を Koitohan のファイルで置き換えて、クライアントごとに `auth-detail` と `reply-detail` の1ファイルずつとし、ほかのログと同じ仕組みに載せた。
- FreeRADIUS は、detail ログが別の名前に移されると、次の書き込みで同じ名前のファイルを作り直す。再オープンの指示は要らない。この動作はスモークテストで確かめている（5.6 節）。
- 置き換える前に作られた日付入りのファイルは、そのまま残る。月と日がともに2桁のもの（`auth-detail-2026-10-10`）だけは、logrotate が切り替え済みのファイルと見なし、圧縮と削除の対象にする。切り替えの当日だけは、同じ名前のファイルが先にあると logrotate がその日の切り替えを見送るが、翌日にまとめて切り替わる。

**tftpd-hpa**

- 転送の記録（6.3 節）は、コンテナの中の `syslogd`（busybox）が書く。`syslogd` はファイルを1秒ごとに開き直すので、別の名前に移されると、同じ名前のファイルを作り直す。再オープンの指示は要らない。この動作はスモークテストで確かめている。
- 移した直後の1秒に届いた記録は、移したあとのファイルに入る。直前の1日分を圧縮しない（`delaycompress`）ので、失われない。
- `syslogd` は root で動くので、ファイルは root の所有になる。`su` には 0 を指定する。

### 6.3 TFTP の書き込み制限と転送の記録

TFTP には認証がなく、69/udp に到達できる相手は誰でも `configs/` に書き込める。書き込みが Docker ホストのディスクを使い切ると、ログの保存や LDAP のデータベース、ホスト自体が停止する。これを避けるため、次の2つを併用する。

| 制限               | 方法                                                    | 設定                               |
| ------------------ | ------------------------------------------------------- | ---------------------------------- |
| 総量とファイル数   | 固定サイズのループバックイメージを `configs/` にマウント | Docker ホスト側の作業（`/etc/fstab`） |
| 1ファイルのサイズ  | コンテナの `ulimit`（`fsize`）                           | `.env` の `TFTP_UPLOAD_MAX_BYTES`  |

**ループバックイメージ**

- イメージファイルは `tftpd-hpa/configs.img` に置く。公開するツリー（`tftpboot/`）の外に置き、TFTP で配布されないようにする。
- マウントポイント（`tftpd-hpa/tftpboot/configs`）の下のディレクトリは root の所有とし、マウントした側のルートだけを uid 1000 の所有とする。  
  イメージがマウントされていないときは、書き込みがホストのディスクに落ちずに失敗する。
- マウントポイントはリポジトリで管理しない。管理すると、クローンした利用者の所有で作成され、上記の保護が働かないためである。
- 作成には root 権限が必要であり、構築スクリプトには含めない。手順は運用ガイド（`docs/tftp.md`）に記載し、実施を強く推奨する。

次の方式は採用しなかった。

- ext4 のプロジェクトクォータ: ルートファイルシステムの機能を有効にする必要があり、導入の手間が大きい。
- uid 1000 のユーザークォータ: syslog-ng や利用者自身の書き込みも制限してしまう。
- tmpfs: 再起動でバックアップが失われる。

**1ファイルのサイズ**

- 既定は 16MB とする。コンフィグのバックアップには十分であり、tech-support の出力やダンプを受ける環境では値を上げる。
- `firmware/` からの配布は読み出しであり、この制限の対象外である。
- 上限を超えた転送は、サーバのプロセスが終了させられる形で止まる。  
  機器にはエラーが返らずタイムアウトとなり、上限サイズの書きかけのファイルが残る。ログにも記録されない。

**接続元**

要求を受け付ける送信元は、機器のネットワーク（`.env` の `DEVICE_NETWORKS`）に限定する。方法は 8 節の「接続元の制限」に記載する。  
書き込める容量の制限は、この範囲の中にいる相手に対するものとして残す。

**転送の記録**

`in.tftpd` は、要求ごとに、種類（取得は `RRQ`、アップロードは `WRQ`）、要求元のアドレス、ファイル名を syslog に出力する（`--verbose`）。出力先は syslog だけなので、コンテナの中で busybox の `syslogd` を動かし、次の2か所に書かせる。

| 出力先                                                          | 用途                                         |
| --------------------------------------------------------------- | -------------------------------------------- |
| `/var/log/tftpd/tftpd.log`（ホスト側では `tftpd-hpa/log/tftpd.log`） | 保存。6.2 節のローテーションの対象とし、3年分を残す |
| コンテナの標準出力                                              | `docker compose logs tftpd-hpa` での確認     |

- 出力先は、イメージの中の `/etc/syslog.conf`（`tftpd-hpa/build/syslog.conf`）に書く。`syslogd` のオプションで指定できる出力先は1つだけである。
- `syslogd` は、既定ではファイルが 200KB を超えると自分で切り替え、1世代しか残さない。これを止め（`-s 0`）、切り替えは Docker ホストの logrotate に任せる。
- 時刻は `syslogd` が `TZ` に従って付ける。年は入らないので、切り替えたあとのファイル名の日付で補う。
- 記録は要求の時点のものであり、転送が最後まで済んだかどうかは残らない。上限を超えて止まった転送（上記）も、要求の記録だけが残る。
- ファイルは root の所有、パーミッション 0644 とする。利用者作業用コンテナ（7 節）にはマウントしない。

次の方式は採用しなかった。

- syslog-ng のコンテナへ転送する: `syslogd` の送り先は1つで、コンテナの標準出力と両立しない。syslog-ng の接続元の制限（`DEVICE_NETWORKS`）に、Docker のネットワークを含める必要も生じる。
- 標準出力をパイプで受けて `tee` でファイルに書く: `tee` はファイルを開いたままにするので、切り替えに `copytruncate` が要り、切り替えのあいだの行を失うことがある。

### 6.4 コンテナの標準出力

ファイルに書かれず、コンテナの標準出力にだけ出るログがある。利用者作業用コンテナのログインの記録（sshd、`nslcd`、PAM。7.9 節）と、OpenLDAP のログが、これにあたる。tftpd-hpa の転送の記録も標準出力に出るが、同じものをファイルにも保存している（6.3 節）。

これらの保存と上限は Docker のログドライバに任せ、`compose.yaml` には `logging:` を書かない。全サービスに共通の設定を置くことを検討したが、次の理由で見送った。

- ログドライバのオプションは、ドライバごとに異なる。たとえば `max-size` を `journald` に渡すと、コンテナが起動しない（`unknown log opt 'max-size' for journald log driver`）。共通の `logging:` を書くには、ドライバも固定することになる。
- ドライバを固定すると、Docker ホストの設定（`/etc/docker/daemon.json`）を上書きする。ホストのログをどこに集めるかは、ホストごとに決めることである。
- 検証環境は `journald` を使っている。上限は journald が管理し、`docker compose logs` でも `journalctl CONTAINER_NAME=<コンテナ名>` でも読める。
- Docker の既定の `json-file` は、指定しないかぎりローテーションしない。この場合は、`daemon.json` でドライバを `local` か `journald` に変えるか、`json-file` に `max-size` と `max-file` を指定する。運用ガイド（`docs/logs.md`）に記載する。

**課題**

- これらの記録が残る期間は、ログドライバの上限（容量）で決まり、日数では決まらない。6.2 節の3年保持の対象ではない。

## 7. 利用者作業用コンテナ（基本設計）

パスワード認証によるログインと、4.7 節のスクリプトとの連携を実装済みである。公開鍵認証（7.6 節）は、必要性を確かめるまで実装を保留する。設計と実装の対応は 7.9 節にまとめる。

### 7.1 提供する機能

ユーザは SSH で利用者作業用コンテナにログインし、次の作業を行う。

| 作業                         | 対象のユーザ        |
| ---------------------------- | ------------------- |
| ログの閲覧、絞り込み、取得   | すべてのユーザ      |
| 自身のパスワードの変更       | すべてのユーザ      |
| TFTP のファイルの配置と取得  | ロール `admin` のみ |

Docker ホスト自身の sshd とは別のポートで公開し、番号は `.env` で指定する（`OPENSSH_PORT`）。

利用の例：

```sh
# 全機器の 2026-10-10 のログから、特定のメッセージだけを取り出す
ssh -p 2222 user@koitohan 'zgrep -h LINK-3 /logs/Hosts/*/*.log-2026-10-10.gz' > link.txt

# 複数の機器の、特定の期間のログをまとめて取得する
scp -P 2222 'user@koitohan:/logs/Hosts/sw-*/*.log-2026-10-1*.gz' .
```

### 7.2 ロールと権限

| ロール     | ログ     | `configs/` | `firmware/` |
| ---------- | -------- | ---------- | ----------- |
| `admin`    | 読み取り | 読み書き   | 読み書き    |
| `operator` | 読み取り | なし       | なし        |
| `readonly` | 読み取り | なし       | なし        |

- ログは、ロールや機器による閲覧の制限を設けない。
- `firmware/` に書き込めるユーザは、機器が取り込むイメージを差し替えられる。これは機器の管理者権限に相当するため、`admin` に限る。
- `configs/` のコンフィグには、パスワードのハッシュや共有シークレットが含まれる。読み取りも `admin` に限る。

権限は OS のグループとファイルのパーミッションで分ける。コンテナの中では、ロールを次の固定の GID に対応させる。

| グループ             | GID   | グループ名 |
| -------------------- | ----- | ---------- |
| 全ユーザ共通         | 10000 | `koitohan` |
| ロール `admin`       | 10001 | `admin`    |
| ロール `operator`    | 10002 | `operator` |
| ロール `readonly`    | 10003 | `readonly` |

GID もファイルに数値で残るため、後から変更しない。

どのロールにも所属していないユーザは、ログインできない。ネットワーク機器へのログインでの扱い（5.3 節）に合わせる。`/etc/passwd` には、ロールに所属するユーザだけを書き出す。

複数のロールに所属しているユーザは、そのうちいちばん弱いロール（`readonly`、`operator`、`admin` の順）のグループにだけ入れる。これも 5.3 節に合わせる。たとえば `readonly` と `admin` の両方に所属するユーザは、`configs/` と `firmware/` を使えない。

`/etc/passwd` と `/etc/group` を作り直すのは、次のときである。定期的な作り直しはしない。

- コンテナの起動時。
- 4.7 節のスクリプトが、ユーザの登録、削除、ロールの変更を行ったとき。変更の入口がこのスクリプトだけなので、反映の漏れも遅れも生じない。
- こいとはん管理者が手で実行したとき。スクリプトを通さずに LDAP を書き換えた場合は、こうして反映する。

ロールの変更は、ログイン中のセッションには及ばず、次のログインから効く。そのため、4.7 節のスクリプトは、ユーザの削除とロールの変更のときに、そのユーザのログイン中のセッションを切る。

- LDAP の変更、`/etc/passwd` と `/etc/group` の作り直し、セッションの切断の順に行う。切断したあとでユーザがログインし直すと、新しい状態が効く。
- 切断は、コンテナの中で、そのユーザの UID のプロセスをすべて終了させて行う。UID は、削除の前に LDAP から読んでおく。

### 7.3 マウント

| ホスト側                       | コンテナ内のパス      | コンテナでの扱い |
| ------------------------------ | --------------------- | ---------------- |
| `syslog-ng/log/Hosts/`         | `/logs/Hosts/`        | 読み取り専用     |
| `tftpd-hpa/tftpboot/configs/`  | `/tftpboot/configs/`  | 読み書き         |
| `tftpd-hpa/tftpboot/firmware/` | `/tftpboot/firmware/` | 読み書き         |

- tftpd-hpa のコンテナ側は変更しない。`firmware/` は引き続き読み取り専用でマウントし、機器からの書き込み先を `configs/` に限る。
- `configs/` への書き込みには、ループバックイメージによる総量の制限（6.3 節）がそのまま効く。
- `firmware/` には容量の制限を設けない。書き込めるのは認証を経た `admin` のユーザだけであり、それで足りると判断した。
- syslog-ng のデバッグログ（`debug.log`）と FreeRADIUS のログは見せない。

配置したファームウェアの照合には、busybox に含まれる `md5sum` / `sha1sum` / `sha256sum` / `sha512sum` を使う。

### 7.4 コマンドと隔離

使えるコマンドの一覧を定めて制限することはしない。`awk` は `system()` で、`sed` は `e` コマンドで任意のコマンドを実行できるため、一覧による制限は成り立たない。  
制限は、コンテナの構成でかける。

- ログは読み取り専用でマウントする。
- ルートファイルシステムを読み取り専用にする。
- ユーザは非 root で動かし、`no-new-privileges` を付ける。
- プロセス数、メモリ、CPU に上限を設ける。  
  メモリの上限は、Docker ホストで cgroup のメモリコントローラが有効なときにだけ効く。Raspberry Pi OS の既定では無効である。有効にする作業は、構築の任意の手順として運用ガイド（`docs/ssh.md`）に記載する（7.7 節）。
- 専用のネットワークで OpenLDAP とだけつなぎ、FreeRADIUS、syslog-ng、tftpd-hpa には届かないようにする。
- コンテナから外への通信は、既定では OpenLDAP の 636/tcp だけに絞る。こいとはん管理者は、制限しない設定も選べる（7.8 節）。

### 7.5 パスワードの変更

ユーザは、ログインしたシェルの中のコマンドで自身のパスワードを変更する。

- 現在のパスワードを確認したうえで、新しいパスワードを 4.8 節の規則で判定する。
- 判定を通ったものだけを OpenLDAP に送る。
- ハッシュ化は OpenLDAP に任せ、コンテナはハッシュを扱わない。

この判定をシェルから迂回できることは、4.8 節のとおりである。

### 7.6 公開鍵認証【保留】

実装を保留する。公開鍵認証によるログインが必要になるかどうかが、まだわからないためである。ユーザから要望が上がり、必要性を確かめたうえで実装する。  
実装する場合の方式は次のとおり決め、試作で成り立つことを確かめた（7.7 節）。

**方式**

- 公開鍵は LDAP のユーザのエントリに置く（`sshPublicKey` 属性）。OpenLDAP のパッケージには、この属性を定める openssh-lpk のスキーマが含まれていないので、LDIF を用意して加える。
- sshd は `AuthorizedKeysCommand` により、ログインのたびに LDAP から鍵を引く。鍵の登録や削除のあとに、`koitohan-update-users` もコンテナの作り直しも要らない。
- 検索に使うサービスアカウント `openssh-keys` を `ou=ServiceAccounts` に追加する。パスワードは、ほかのサービスアカウントと同じく `secrets/` に置く（4.10 節）。
- クライアント証明書は、このコンテナのもの（`openssh_client`）を使う。証明書が表すのは接続元のコンテナであり、読める範囲はサービスアカウントで決まる。証明書を分けても権限は分かれない。
- 鍵を引くコマンドは、専用の非 root ユーザ（`AuthorizedKeysCommandUser`）で動かす。証明書の写しと bind 用のパスワードは、そのユーザだけが入れるディレクトリに置き、ログインしたユーザからは読めないようにする（`nslcd` と同じ方法）。
- パスワード認証と併用する。鍵を登録したユーザも、パスワードでログインできる。
- 受け付ける鍵は、ed25519 と、2048 ビット以上の RSA とする（`PubkeyAcceptedAlgorithms`、`RequiredRSASize`）。

**パスワードポリシーのロック**

公開鍵認証は LDAP の bind を通らないので、そのままでは、ロックされたユーザ（4.8 節）も鍵でログインできる。鍵を引くコマンドが `pwdAccountLockedTime` を読み、ロック中なら鍵を返さない。

- `pwdAccountLockedTime` は、ロックの期間を過ぎても残る。消えるのは、次にパスワードの bind が成功したときである。属性の有無だけで判定すると、期間を過ぎたあとも、パスワードで一度ログインするまで鍵でログインできない。これを避けるため、ユーザに割り当てたポリシーの `pwdLockoutDuration` から期限を計算する。
- PAM の account の段（`nslcd` の `pam_authz_search`）で判定する方式は採らない。検索のフィルタは現在の時刻を扱えず、属性の有無でしか判定できないため、上の動作になる。
- ロック中の応答は鍵が合わないときと同じになり、ロックされていることは相手に伝わらない。

**鍵の登録**

- 鍵の登録は、こいとはん管理者がスクリプトで行う。ユーザ本人に登録させると、パスワードが漏れたときに、鍵まで置かれる経路になる。パスワードを変えても、置かれた鍵は残る。
- ユーザは公開鍵をこいとはん管理者に渡し、フィンガープリントを別の経路で伝える。こいとはん管理者は、登録の前にフィンガープリントが一致することを確かめる。
- ユーザ自身の操作を加えるときは、申請と承認の形にする。ユーザがログインしたコンテナの中で鍵を申請し、こいとはん管理者がフィンガープリントを本人に確かめてから承認する。  
  ユーザはクライアント証明書の秘密鍵を読めないので（7.7 節）、ユーザ自身に登録させるには、LDAP への書き込みを仲介するデーモンが要る。パスワードでログインしたユーザに登録させる形は、上の理由で採らない。鍵でログインしたセッションからだけ登録させる形は、仲介に加えて認証の経路を確かめる仕組みが要り、作り込みが大きいので採らない。

### 7.7 検証事項

実装の前に、試作で次の点を確かめる。稼働中のスタックには触れず、別のプロジェクトとして起動する。

**確認済み**

- **LDAP のユーザを OS のユーザとして扱う方法**: `ou=People` から `/etc/passwd` と `/etc/group` を生成し、認証だけを PAM から LDAP に問い合わせる方式が成り立つ。  
  Alpine 3.24 のパッケージ（`openssh-server-pam` と、`nslcd` および `pam_ldap` を含む `nss-pam-ldapd`）で足り、スクリプト言語を必要としない。
  - ロールは、`ou=Roles` の `uniqueMember` から 7.2 節の GID のグループに対応づけられる。
  - `no-new-privileges` を付けたままで動く。
  - 生成したファイルは、作り直すまで LDAP の変更を反映しない。起動後に登録したユーザは、作り直すまでログインできない。
  - 削除したユーザは、生成したファイルに行が残っていても、認証が失敗するのでログインできない。
  - musl libc が NSS の代わりに問い合わせる nscd（`musl-nscd`）を使えば、LDAP を都度引くこともできる。しかし、ロールが `gidNumber` を持たないため OS のグループにならず、4.9 節の方針と合わない。採用しない。
- **OpenLDAP への接続**: OpenLDAP はクライアント証明書を要求する（4.5 節）。このコンテナ用の証明書を発行する。
  - 証明書と秘密鍵は、root だけが入れるディレクトリにマウントし、起動時に `nslcd` 専用のディレクトリへ写す。この構成で、ユーザのシェルから秘密鍵と bind 用のパスワードを読めないことを確かめた。
  - CA 証明書とクライアント証明書も `nslcd` が読める場所に置く。読めないと、すべてのユーザの認証が失敗する。
  - 証明書の要求は、Docker ネットワークの中から平文の 389 につなぐ相手には効いていなかった。ログインしたユーザはこのネットワークから OpenLDAP に届くため、TLS を使わない操作を拒否する設定を加えた（4.5 節）。その後、イメージを自前でビルドする形に改め、389 の待ち受けそのものをなくした。
- **passwdqc**: Alpine 3.24 のパッケージにはないが、ソースからビルドできる。
  - passwdqc 2.0.3 と 2.1.0 が、`build-base` と `linux-pam-dev` だけでビルドできる。2.1.0 を使う。ビルドと実行でステージを分ければ、実行側に要るのは `pwqcheck`、`pam_passwdqc.so`、ライブラリと、`linux-pam` のパッケージである。
  - `pwqcheck` は `min=12,10,10,8,8` で、4.8 節の表のとおりに判定する。境界の長さ（3種類の 7 と 8、2種類の 9 と 10、1種類の 11 と 12）と、`Password1` の拒否を確かめた。
  - 非 root、読み取り専用のルートファイルシステム、`no-new-privileges` のままで動く。
  - Alpine の PAM のモジュールは `/usr/lib/security` にある。passwdqc の既定のインストール先（`/lib/security`）とは異なるので、インストール先を指定する（`SECUREDIR=/usr/lib/security`、`SHARED_LIBDIR=/usr/lib`）。
  - `passwd` の PAM の並びを、`pam_passwdqc.so`（`requisite`）、`pam_ldap.so`（`use_authtok`）の順にすると、7.5 節のとおりに働く。
    - 規則に合わないパスワードは `pam_passwdqc.so` が拒否し、理由をユーザに表示する。`nslcd` にも OpenLDAP にも送られず、パスワードは変わらない。
    - 規則に合うパスワードだけが、パスワード変更の拡張操作で送られる。変更のあとは、新しいパスワードでだけ bind できる。
    - 現在のパスワードを誤ると、新しいパスワードを尋ねる前に失敗する。
    - 現在のパスワードをもとにした新しいパスワード（末尾に文字を足したものなど）も拒否される。
    - 入力した2回が一致しないときも、変更されない。
  - 判定の設定は1つのファイル（`/etc/passwdqc.conf`）に置き、`pam_passwdqc.so` と `pwqcheck` の両方に `config=` で読ませられる。4.7 節のスクリプトと `passwd` が、同じ設定で判定する。
  - 既定では、拒否のあとに規則の説明（英語）と、無作為に生成したパスフレーズの候補が表示される。候補の表示は `random=0` で止められるが、止めない。規則に合うパスワードを決める助けになるためである。
  - `passwd` への入力は、端末からではなく標準入力から与えて確かめた。SSH でログインした端末からの操作は試していない。ppolicy を有効にした OpenLDAP との組み合わせは、実装のあと、スモークテストで確かめている（4.8 節）。
- **ホームディレクトリ**: 実体を持たせない。要望があれば、あらためて方法を検討する。
  - ディレクトリがなくてもログインできる。作業ディレクトリは `/` になる。
  - `homeDirectory` 属性は 4.9 節のとおり持たせる。
  - `scp` と `sftp` は、コンテナ側のパスを絶対パスで指定して使う。
  - 中間ファイルの置き場所として、容量を絞った tmpfs を `/tmp` に用意する。内容はコンテナを作り直すと消えるので、残したい結果は手元に取得する。  
    tmpfs に書いた分はコンテナのメモリの上限（7.4 節）に数えられるため、容量は上限よりも十分に小さくする。
- **ppolicy**: Alpine のパッケージ（`openldap-overlay-ppolicy`）で使える。OpenLDAP 2.6 ではスキーマがモジュールに含まれており、2.4 向けに書いた LDIF がそのまま通る。最小の長さとロックは 4.8 節のとおりに働く。
  - 最小の長さは、パスワード変更の拡張操作でも、`userPassword` の直接の書き換えでも、エントリの追加でも判定される。平文で書き込まれた値は OpenLDAP がハッシュ化して保存する（`olcPPolicyHashCleartext`）。
  - ハッシュ済みの値は、`pwdCheckQuality: 2` にすると長さにかかわらず拒否される。`1` では受け付けられ、最小の長さを迂回できる。`2` を使う。
  - ロック中は、正しいパスワードでも誤ったパスワードと同じ応答（`Invalid credentials`）になり、ロックされていることは相手に伝わらない。
  - 失敗の回数は、認証に成功すると 0 に戻る。失敗を数える期間を過ぎた失敗は数えない。
  - ロックは、時間の経過のほか、`pwdAccountLockedTime` の削除と、パスワードの再発行で解除される。
  - サービスアカウントは、ロックを無効にした別のポリシーを `pwdPolicySubentry` で割り当てることで、対象から外せる。
  - ユーザ本人は、ポリシーも、自身に割り当てるポリシーも書き換えられない。
  - rootdn（`cn=admin`）による書き込みは、ポリシーの判定をすべて素通りする。コンテナ内の `ldapi:///` の root は判定を受ける。  
    4.7 節のスクリプトは `ldapi:///` を使い、パスワードを平文で渡す。こうすると、スクリプトが発行するパスワードにも OpenLDAP の判定がかかる。
  - 初期投入では、順序に制約がある。ポリシーのエントリは、モジュールを読み込んだあとでないと追加できない（`pwdAttribute` の構文エラーになる）。オーバーレイを有効にしたあとは、ハッシュ済みのパスワードを持つ LDIF（サービスアカウント）が拒否され、OpenLDAP が起動に失敗する。  
    そのため、アカウントの LDIF のあと、ACL の前に、モジュールとオーバーレイ、ポリシーのエントリ、サービスアカウントへの割り当ての順で投入する。
  - 稼働中のデータベースにも、`ldapi:///` から同じ内容を適用できる。データベースを消す必要はない（4.6 節）。
- **パスワードの変更の実現方法**: 認証用のデーモン（`nslcd`）を経由する。ユーザが `passwd` を実行すると、PAM の `pam_ldap` が `nslcd` に依頼し、`nslcd` がユーザ本人として bind して、パスワード変更の拡張操作を送る。
  - Alpine 3.24 のパッケージで足りる。`passwd` は `shadow` パッケージのものを使う（PAM に対応している）。
  - LDAP に直接つなぐ方式は採らない。ユーザはクライアント証明書の秘密鍵を読めないため、636 でも、389 の StartTLS でも、接続が成立しない。秘密鍵を使えば同じ操作が通ることも確かめており、妨げているのは証明書だけである。
  - `passwd` は setuid なしで動く。`no-new-privileges` を付けたままでよい。
  - 新しいパスワードは平文のまま拡張操作で送られ、ハッシュ化は OpenLDAP が行う（7.5 節）。
  - ユーザ本人の bind で変更するため、ppolicy の判定がかかる。最小の長さに満たないパスワードは拒否され、その旨がユーザに表示される。
  - 現在のパスワードを誤ると変更されず、ロックのための失敗として1回数えられる。
  - `passwd` は、ほかのユーザを指定した変更を受け付けない。

- **`in.tftpd` との共存**: 両立できる。`firmware/` と `configs/` を、所有者 uid 1000（`in.tftpd`）、グループ GID 10001（ロール `admin`）、パーミッション 2770 にする。
  - `in.tftpd` は所有者として、`admin` のユーザはグループとして入れる。ほかのユーザは入れないので、7.2 節の権限がこの2つのディレクトリだけで決まる。
  - setgid により、中に作られるファイルのグループは 10001 になる。
  - `admin` のユーザが置いたファームウェアは、機器から取得できる。ただし、ファイルに「その他」の読み取り権限が要る。0600 で置くと `in.tftpd` が読めず、機器には `Permission denied` が返る。`chmod 644` で直る。
  - 機器がアップロードしたコンフィグ（所有者 1000、0644）を、`admin` のユーザは読み、複製し、名前を変え、削除できる。その場での書き換えはできない。`in.tftpd` の `--umask` を 002 にすれば、書き換えもできる。
  - `admin` のユーザが `configs/` に置いたファイルは、機器から取得できる。機器からの上書きはできない（`Permission denied`）。上書きさせるには、先に削除する。
  - `admin` のユーザどうしは、互いのファイルを置き換え、削除できる。
  - `firmware/` への機器からの書き込みは、これまでどおり読み取り専用のマウントで拒否される。
- **読み取り専用のルートファイルシステム**: 7.4 節の構成で動く。起動時に書き込むものはすべて `/run`（tmpfs）に置き、`/etc/passwd`、`/etc/group`、`/etc/nslcd.conf` は、イメージの中でそこへのシンボリックリンクにしておく。
  - sshd、`nslcd`、`passwd`、`scp`、`sftp` が動く。sshd には PID ファイルを作らせず、`sftp` は sshd に内蔵のものを使う。  
    Alpine の `openssh-server-pam` では、sshd の実行ファイルは `sshd.pam` である。
  - ユーザが書き込めるのは `/tmp` だけである。容量を超える書き込みは失敗し、置いたファイルは実行できない。
  - `/etc/passwd` と `/etc/group` は、コンテナを止めずに作り直せる。起動後に登録したユーザも、作り直したあとはログインできる。
  - プロセス数の上限はコンテナ全体にかかる。1人が使い切ると、ほかのユーザはログインできなくなる。  
    PAM の `pam_limits` でユーザごとの上限を加えると、ほかのユーザはログインできる。`limits.conf` の対象は `*` で指定する。グループ（`@users`）で指定したときは効かなかった（原因は調べていない）。
- **メモリの上限**: Docker ホストで cgroup のメモリコントローラを有効にすれば効く。
  - Raspberry Pi OS の既定では、カーネルの起動オプションに `cgroup_disable=memory` が付いている。RAM の少ない機種に合わせた既定である。このあいだ、Compose で指定したメモリの上限は無視され、`docker info` は `No memory limit support` と警告する。
  - `/boot/firmware/cmdline.txt` の行の末尾に `cgroup_enable=memory` を加えて Docker ホストを再起動すると、有効になる（Raspberry Pi 5、Raspberry Pi OS trixie、カーネル 6.18 で確かめた）。`/sys/fs/cgroup/cgroup.controllers` に `memory` が加わり、警告は消える。
  - 再起動のあと、稼働中のコンテナは自動で戻る。
  - 上限を超えたプロセスは強制終了される。コンテナは動き続け、ほかのプロセスは残る。
  - tmpfs に書いた分は、上限に数えられる。上限より大きい tmpfs に書き続けると、上限に達したところで、書いていたプロセスが強制終了される。上限より小さい tmpfs では、容量が尽きた時点で書き込みが失敗するだけである。`/tmp` の容量を上限より十分に小さくする方針（上の「ホームディレクトリ」の項）は、これに合う。
  - スワップを合わせた上限（`--memory-swap`）を、メモリの上限と同じ値にして試した。スワップの上限を指定しない場合は試していない。
  - 有効にしないあいだは、ユーザのプロセスが使うメモリに歯止めがない。プロセス数の上限と、`/tmp` の容量の制限は効く。
- **ログイン中のセッションの切断**: コンテナの中で root が `pkill -KILL -u <UID>` を実行すると、そのユーザのセッションだけが切れる。
  - ユーザの側では、接続がサーバから閉じられる。ほかのユーザのセッションは残る。
  - sshd がセッションごとに持つ root のプロセスは、ユーザの側のプロセスが終わると自分で終了する。
  - `pkill` は busybox に含まれる。読み取り専用のルートファイルシステムと `no-new-privileges` のままで動く。
- **sshd のホスト鍵**: Docker ホストで生成し、コンテナには読み取り専用でマウントする。コンテナを作り直しても鍵は変わらず、ユーザの手元で警告は出ない。
  - マウント先は、証明書と同じく root だけが入れるディレクトリにする。ユーザのシェルからは読めない。
  - 鍵のファイルは、ホストで生成したままの所有者（ホストの一般ユーザ）と 0600 で、sshd が読み込める。
  - 生成は証明書と同様に `make` で行い、鍵は git の追跡から外す。
- **コンテナから外部への通信の制限**: コンテナ自身のパケットフィルタで絞れる（Docker 29.7.2、Alpine 3.24 の `iptables`）。7.8 節の決定により、nftables で実装した（7.9 節）。
  - Docker の `internal: true` のネットワークは使えない。ポートを公開できず、sshd にホストの外から届かなくなる。また、ブリッジのゲートウェイのアドレスを通じて、Docker ホスト自身のポート（ホストの sshd など）には届く。
  - 起動時に root が `OUTPUT` チェーンの既定を破棄にし、ループバック、確立済みの通信への応答、同じサブネットの 636/tcp だけを許可する。IPv6 も同様に閉じる。コンテナに `NET_ADMIN` のケーパビリティが要る。
  - この構成で、ユーザからは OpenLDAP の 636 にだけ届く。OpenLDAP の 389、Docker ホスト（ゲートウェイのアドレス、LAN 側のアドレス）の 22、インターネットには届かない。公開したポートへの外からの接続は通る。
  - 宛先はサブネットで指定するので、OpenLDAP の IP を固定しなくてよい。ゲートウェイのアドレスの 636（Docker ホストが公開している OpenLDAP）にも届くが、相手は同じ OpenLDAP である。
  - ユーザはルールを変えられない（`Permission denied`）。ルールを入れたあとは、`setpriv` で `NET_ADMIN` を落としてからデーモンを起動できる。
  - 名前解決は通る。Docker の内蔵 DNS への問い合わせはループバックの通信だからである。外部の名前も引けるので、DNS の問い合わせに載せた持ち出しまでは止まらない。
  - 読み取り専用のルートファイルシステムと `no-new-privileges` のままで動く。
  - sshd の代わりに `nc` の待ち受けを、ユーザのシェルの代わりに非 root の `docker exec` を使って確かめた。sshd と `nslcd` を入れた構成では試していない。
- **公開鍵認証**: 7.6 節の方式が成り立つ（OpenLDAP 2.6.15、OpenSSH 10.3p1）。実装は保留している。
  - Alpine の OpenLDAP のパッケージには openssh-lpk のスキーマがない。自前の LDIF で加えられる。稼働中のデータベースには `ldapi:///` からの追加で、新しいデータベースには初期投入の `slapadd` での読み込みで入る。
  - 現在の ACL（4.3 節）のままで、サービスアカウントは鍵、`pwdAccountLockedTime`、ポリシーのエントリを読める。ユーザ本人による `sshPublicKey` の書き込みは拒否される（`Insufficient access`）。
  - ed25519 と、2048 ビットと 4096 ビットの RSA の鍵でログインできる。1024 ビットの RSA と ECDSA の鍵は、sshd が拒否する。
  - ロック中は、鍵でログインできない。ロックの期間を過ぎると、パスワードでログインしなくても、鍵でログインできる。期限の計算は、busybox の `date`（`-D` で書式を指定）で行える。
  - 手でかけたロック（`pwdAccountLockedTime` が `000001010000Z`）のあいだもログインできず、4.7 節のスクリプトの `unlock` で戻る。
  - 鍵でログインしても、`pwdAccountLockedTime` は消えない（bind を通らないため）。期限で判定するので差し支えない。
  - ユーザを削除すると、鍵でもログインできなくなる。
  - OpenLDAP が止まっているあいだは、待たされずに拒否される。応答しない相手は試していないので、検索には時間の上限（`ldapsearch` の `-o nettimeout=`）を付ける。
  - 鍵のコメントに ASCII 以外の文字（日本語など）があると、`ldapsearch` は値を base64 で出力する（`sshPublicKey::`）。鍵を引くコマンドで復号する。
  - 鍵を引くコマンドのユーザの持ち物（証明書の写しと bind 用のパスワード）は、ログインしたユーザから読めない。ログインしたユーザがコマンドを実行しても失敗する。`no-new-privileges` と読み取り専用のルートファイルシステムのままで動く。
  - パスワード認証は、公開鍵認証と並べても変わらずに働く。

### 7.8 課題

- **コンテナから外部への通信**: 止めるかどうかを、こいとはん管理者が `.env` の `OPENSSH_EGRESS` で選べるようにした。`ldaps`（既定）は OpenLDAP の 636/tcp だけを許し、`any` は syslog と TFTP（514/tcp、514/udp、69/udp）を除いて制限しない。どちらの値でも、許さない通信は落とさずに断る。ユーザの手元で、タイムアウトを待たずにすぐ失敗させるためである（ユーザから違いが見えるのは TCP だけで、コンテナから出ていく ICMP と UDP は、落としても断っても送信が EPERM で失敗する）。実装は 7.9 節。  
  止める効果は、利用者の端末のネットワーク（`OPENSSH_ALLOWED_NETWORKS`）と機器のネットワークを分けているかどうかで変わる。それを知っているのは、こいとはん管理者だけである。
  - 分けている場合、このコンテナは2つのネットワークをつなぐ。sshd のポートフォワーディングを止めていても、`nc` を中継に使えば（`ssh -o ProxyCommand="ssh koitohan nc %h %p" 機器`）、端末から機器に入れる。
  - 分けていない場合、ユーザは同じ認証でネットワーク機器にもログインでき、機器からも同じように外へ出られる。このコンテナだけを閉じる効果は限られる。
  - どちらの場合も、`ldaps` なら Docker ホスト自身のポート（ゲートウェイのアドレスを通じて届く。ホストの sshd など）とインターネットには届かない。

  一方で、このコンテナを機器への踏み台として使う用途もありうる。`any` はそのための値で、ローカルのポートフォワーディング（`ssh -J`、`ssh -L`）も許す。止めても `nc` で同じことができ、効果がないからである。リモートのフォワード、エージェントの転送、X11 の転送、トンネルは、どちらの値でも止める。踏み台に要らず、エージェントの転送は利用者の手元の鍵を中継先にさらす。  
  ポートフォワーディングを別の設定にしなかったのは、守りが増えないためである。`ldaps` では、フォワードの接続を開く sshd にもパケットフィルタが掛かる。`any` では、`nc` で同じことができる。

  `any` でも syslog と TFTP を断るのは、このコンテナが Koitohan 自身のサービスへの中継になるためである（2026-10-18 にテスト用のスタックで確かめた）。
  - ユーザは、Docker ホストが公開している syslog-ng と tftpd-hpa のポートに、Docker ホストのアドレス（ゲートウェイ、LAN 側のどちらでも）を通じて届く。どちらも認証がなく、ロールによる区別もない。ログインできるユーザは誰でも、機器を装ったログを書け、`configs/` にファイルを作ったり既存のファイルを上書きしたりできる。SSH では `configs/` を `admin` に限っているので、ロールの迂回になる。読み出しも受け付けられるが、いまのイメージの道具（busybox の `nc`）では中身を受け取れなかった。
  - 届いたものは、サービスからはデフォルトネットワークのゲートウェイ、つまり Docker ホスト自身から届いたように見える。`DEVICE_NETWORKS` では Docker ホストからの送信と区別できず、誰がやったかも記録に残らない。
  - 問題になるのは、端末のネットワークと機器のネットワークを分けている場合である。分けていなければ、ユーザは自分の端末から同じことができる。踏み台として使う場合も、Koitohan 自身の syslog と TFTP に届く利点はない（ファイルはコンテナの中の `/tftpboot` で扱える）。
  - 止め方は、宛先のアドレスを問わずポートの番号で断ることにした。Docker ホストの LAN 側のアドレスはコンテナからはわからず、アドレスで止めるには `.env` に書いてもらうか、Docker ホストのファイアウォール（8 節で避けた方式）に頼ることになる。代わりに、機器の syslog と TFTP にも届かなくなるが、踏み台の用途で要るとは考えにくい。この制限は運用ガイドとユーザーズガイドに書いた。
  - RADIUS（1812/udp）と LDAPS（636/tcp）の公開ポートにも届くが、共有シークレットとクライアント証明書が要るので断っていない。
- **踏み台としての作り込み**: 次の3つは、要望が出てから検討する（保留）。いまの想定では、踏み台の行き先は Koitohan で管理するネットワーク機器である。
  - 宛先の制限。`any` のとき、届く先を機器のネットワークに絞る。`OPENSSH_EGRESS` に IPv4 のアドレスかプレフィックスを書けるようにするか、`DEVICE_NETWORKS` を使い回す。値を `yes` / `no` ではなく `ldaps` / `any` にしたのは、この拡張のためである。
  - ロールごとの許可。nftables は、ソケットの持ち主の GID で照合できる（`meta skgid`）。たとえば、外へ出られるのを `admin`（GID 10001）に限ることが、パケットフィルタで効く形で書ける。sshd の `Match Group` では、`nc` で迂回される。
  - 接続の記録。誰がどこへ接続したかを残す。`nc` の中継は記録に残らない。sshd がフォワードの宛先を、どのログのレベルで記録するかは確かめていない。
- **DNS による持ち出し**: `ldaps` でも名前解決は通る（7.7 節）。外部の名前も引けるので、DNS の問い合わせに載せた持ち出しまでは止まらない。
- **疎通確認のツールの搭載**: 複数のホストへの ICMP / TCP / UDP の疎通を監視する [NexPinger](https://github.com/jolly-jive/nexpinger) を、このコンテナに載せる案がある。保留とする。  
  載せた場合、使えるのは `OPENSSH_EGRESS=any` の環境だけである。  
  escript 版（約 1.7 MB）を置く方法が候補である。Erlang/OTP 27 以降が要り、Alpine 3.24 には `erlang27`（27.3.4.18）と `erlang28` のパッケージがある。`erlang27` を入れると、イメージは約 73 MiB 大きくなる。動作は確かめていない。
  - 常時監視よりも、トラブルシューティングのための道具である（作者の意見）。宛先はその場で決まる。
  - 設定ファイルは、ホームディレクトリ（次の項目）に置く。いまユーザが書けるのは `/tmp`（全員で共有する tmpfs。作り直すと消える）だけで、仮の置き場でしかない。宛先をコマンドラインで受け取れるように NexPinger の側を変え、設定ファイルなしでも使えるようにする案もある。
  - BEAM はスレッドを多く作り、プロセス数の上限（`pids_limit`）に数えられる。数人が同時に起動すると上限に届くおそれがある（確かめていない）。
  - コンテナは NAT の内側にいて機器と同じリンクにいないので、MAC アドレスの表示は使えない見込みである。
- **ホームディレクトリ**: ユーザごとのホームディレクトリ（`/home/<ユーザ名>`）を設ける。保留とし、NexPinger とあわせて実装する。置くのは一時ファイルと個人の設定（NexPinger の設定ファイル、`.profile` など）で、どちらもユーザの責任で扱うものと整理する。
  - 総量は、`configs/`（6.3 節）と同じく、固定サイズのループバックイメージをマウントして制限する。Docker ホストでの `sudo` の作業（`/etc/fstab`）であり、`make` には含めない。`bin/check_host.sh` で、マウントされていることを確かめる。
  - ユーザごとのクォータは設けない。ext4 のクォータは、ユーザごとの値を root が `setquota` で入れる必要がある。コンテナの中には `CAP_SYS_ADMIN` がなく、Docker ホストで行うと 4.7 節のスクリプトに `sudo` が要るようになる。1人のユーザが総量を使い切りうることは、既知の制限として書く。
  - `noexec,nosuid,nodev` でマウントする（`/etc/fstab` のオプション）。`/tmp` を `noexec` にしているので、永続的に書ける場所に置いたバイナリが実行できては意味がない。シェルスクリプトも `./script.sh` の形では実行できないが、`sh script.sh` のように明示すれば動く。
  - パーミッションは 0700、所有者は本人とする。ロールによる区別はしない。
  - `koitohan-update-users` が書く `homeDirectory` を、`/` から `/home/<ユーザ名>` に変える。LDAP の値を使わない方針（7.9 節）は変えない。
  - 作るのは、ログインのときの `pam_mkhomedir` か、4.7 節のスクリプトの `add` かを、実装のときに決める。前者なら、スクリプトを通さずに足したユーザにも効く。消すのは、4.7 節のスクリプトの `delete` である。`uidNumber` を再利用しないので、消し忘れても、別のユーザに中身が渡ることはない。
  - バックアップ（8 節）には含めない。中身はユーザの責任で扱うものである。
  - 冗長化（12 節）で複数台を動かしても、台のあいだで同期しない。必要なら、ユーザ自身がコピーする。
  - スモークテストは、`configs/` と同じく匿名ボリュームを使う。

### 7.9 実装

サービス名とコンテナ名は `openssh`（コンテナ名は `.env` の `OPENSSH_CONTAINER_NAME`）、イメージは `openssh/build/` からビルドする `koitohan/openssh` である。

コンテナのホスト名は、コンテナ名とは別に `.env` の `OPENSSH_HOSTNAME` で指定する。プロンプトにユーザ名とともに表示し（`alice@koitohan:/logs/Hosts$`）、ユーザがどのサーバにログインしているかを見分けられるようにする。冗長化（12 節）で複数台を動かすときは、台ごとに別の名前にする。指定しないと Docker がコンテナ ID を入れ、作り直すたびに変わる。

**起動の流れ（`entrypoint.sh`）**

1. パケットフィルタを入れ、`NET_ADMIN` を落として自分自身を起動し直す（8 節の「接続元の制限」）。入ってくる側は `OPENSSH_ALLOWED_NETWORKS` からの 22/tcp を、出ていく側は `OPENSSH_EGRESS` が `ldaps` のとき、コンテナのネットワークのサブネット宛ての 636/tcp だけを許し、`any` のとき、宛先を問わず 514/tcp、514/udp、69/udp を断る。許さない通信は、TCP なら RST、それ以外なら ICMP の administratively prohibited で断る。断る番号は `compose.yaml` で公開しているホスト側の番号で、変えるときは揃える。サブネットは `.env` の `OPENSSH_SUBNET` ではなく、コンテナの経路表（`ip -4 route show scope link`）から取る。スモークテストのネットワークは Docker が割り当てるためである。`OPENSSH_EGRESS` が `ldaps` と `any` のどちらでもないときは起動しない。
2. busybox の `syslogd` を起動する。sshd、`nslcd`、PAM の出力をコンテナの標準出力へ流すためである（tftpd-hpa と同じ方法）。
3. `/run/koitohan/`（tmpfs）に、`nslcd.conf`、`nslcd` 用の証明書の写し、bind 用のパスワード、`passwdqc.conf`、sshd の `AllowTcpForwarding`（`sshd_forwarding.conf`。`OPENSSH_EGRESS` が `any` なら `local`、`ldaps` なら `no`）を書き出す。bind 用のパスワードは、マウントされたファイル（`/etc/koitohan/secrets/bindpw`。4.10 節）から読む。
4. `koitohan-update-users` で `/etc/passwd` と `/etc/group` を作る。OpenLDAP が応答するまで繰り返し、一定回数で諦めて終了する。
5. `nslcd` と sshd を起動する。どちらかが終了したらコンテナごと終了し、Docker に起動し直させる。

PID 1 は Docker の init（`init: true`）とし、ユーザが残したプロセスの回収を任せる。

**`/etc/passwd` と `/etc/group` の生成（`koitohan-update-users`）**

- サービスアカウントで `ou=People` を検索し、`posixAccount` を持ち、`memberOf` がロールを指すユーザだけを書き出す。ロールは `uniqueMember` を読まず、FreeRADIUS と同じく `memberOf` から決める。複数のロールを指すときは、いちばん弱いロールのグループにだけ入れる（7.2 節）。
- 次のユーザは書き出さず、理由を出力する。ログイン名として使えない `uid`、イメージに元からあるアカウントと同じ名前、範囲（10000〜59999）の外の `uidNumber`、ほかのユーザと重なる `uidNumber`。
- `gidNumber`、`homeDirectory`、`loginShell` は LDAP の値を使わず、それぞれ 10000、`/`、`/bin/sh` を書く。
  ホームディレクトリを実在しないパスにすると、sshd がログインのたびに警告を表示するため、`/` とした。
- 検索に失敗したときは、元のファイルを残す。ファイルは rename で置き換える。
- こいとはん管理者は `docker compose exec openssh koitohan-update-users` で実行する（7.2 節の「手で実行したとき」）。
- 全ユーザ共通のグループの名前は `koitohan` とした。Alpine には `users`（GID 100）が元からあり、同じ名前にはできない。

**sshd**

- 認証は PAM の `pam_ldap` だけで行う。ログインできるのは、全ユーザ共通のグループを主グループとするユーザに限る（`AllowGroups`）。root と、イメージに元からあるアカウントではログインできない。
- ポートフォワーディングは、UNIX ソケット、エージェント、X11、トンネル、リモートの TCP を無効にした。ローカルの TCP は、`OPENSSH_EGRESS` が `any` のときだけ許す（7.8 節）。`sshd_config` の冒頭で `/run/koitohan/sshd_forwarding.conf` を `Include` する。sshd は最初に読んだ値を使うので、こちらが `sshd_config` の `AllowTcpForwarding no` より優先される。`sshd_config` の値は、ファイルが何も書いていないときの備えである。
- 同じ接続元からの認証の失敗が続くと、sshd がその接続元を一時的に拒否する（`PerSourcePenalties`。OpenSSH の既定の動作）。スモークテストは意図して失敗を重ねるので、テストのときだけ無効にする。
- `scp` は、SFTP を使う現在の方式でも、従来の方式（`scp -O`）でも動く。後者のために `openssh-client-common` を入れている。`ssh` コマンドは入れていない。
- 圧縮されたログ（6.2 節）を読むために、`gzip` パッケージを入れている（`zgrep`、`zless` など）。busybox にあるのは `zcat` だけである。

**上限**

| 項目                     | 値     |
| ------------------------ | ------ |
| プロセス数（コンテナ）   | 256    |
| プロセス数（ユーザごと） | 64     |
| メモリ                   | 256 MB |
| CPU                      | 1 コア |
| `/tmp`                   | 32 MB  |

**ホスト側のパーミッション**

- `firmware/` と `configs/` は、7.7 節のとおり、所有者 uid 1000、グループ GID 10001、パーミッション 2770 にする。`sudo` が要る作業であり、`make` には含めず、README のクイックスタートと運用ガイド（`docs/tftp.md`）に手順を記載する。
- syslog-ng は、機器ごとのディレクトリを 0755 で作るように変更した（`dir-perm`）。それまでの既定は 0700 で、ユーザが読めない。すでにあるディレクトリは、こいとはん管理者が直す。
  これにより、機器のログは Docker ホストのすべてのユーザから読める。

**スモークテスト**

`make test` に、SSH でのログイン（ロールごと、ロールなし、誤ったパスワード）、ディレクトリの権限、圧縮されたログの `zgrep` による読み取り、`passwd` による変更と拒否、OpenLDAP の再起動のあとのログインを加えた。テスト用のスタックはポートを公開しないので、Docker ホストからコンテナのアドレスへ直接 `ssh` する。

外への通信は、`openssh` のネットワークに置いた使い捨ての待ち受け（同じイメージの `nc`）に、ログインしたユーザから TCP と ICMP で、また sshd のフォワード（`ssh -W`）で接続して確かめる。`ldaps` では届かないこと、フォワードは sshd が断ること（`administratively prohibited`。パケットフィルタに落とされた場合と見分けるため）を見る。`any` で作り直したあとは、3つとも届くことを見る。誤った値（空、`none`）では起動しないことも見る。

**7.7 節で試していなかった点**

- `passwd` は、SSH でログインした状態でも 7.7 節のとおりに働く。ただし、端末を割り当てない実行（`ssh ユーザ@ホスト passwd`）に標準入力から与えて確かめたものであり、端末からの対話的な操作は試していない。
- OpenLDAP が再起動したあとも、`nslcd` はつなぎ直し、ログインできる。FreeRADIUS のような異常終了は起きない。

**残っている点**

- sshd は、`/etc/passwd` にないユーザ名でも、でたらめなパスワードで PAM の認証を行う（ユーザの有無を応答の時間から悟らせないための動作）。このため、ロールのないユーザの名前でのログインの試行は、LDAP では bind の失敗になる。この失敗も、ppolicy のロック（4.8 節）の回数に数えられる。
- ユーザの登録、削除、ロールの変更のたびの作り直しと、セッションの切断は、4.7 節のスクリプトが行う。スクリプトを通さずに LDAP を書き換えたときは、こいとはん管理者が手で実行する。

## 8. Docker Compose 構成方針

### コンテナ一覧

| コンテナ     | イメージ                                  | 公開ポート         | 状況     |
| ------------ | ----------------------------------------- | ------------------ | -------- |
| `openldap`   | 自前でビルド（Alpine）                    | 636/tcp            | 実装済み |
| `freeradius` | `cayenneryo/freeradius-server` から派生   | 1812/udp           | 実装済み |
| `syslog-ng`  | `linuxserver/syslog-ng`                   | 514/udp、514/tcp   | 実装済み |
| `tftpd-hpa`  | 自前でビルド（Alpine）                    | 69/udp             | 実装済み |
| `openssh`    | 自前でビルド（Alpine）                    | 2222/tcp           | 実装済み |

最後の行は利用者作業用コンテナ（7 節）である。公開するポートの番号は `.env` の `OPENSSH_PORT` で変えられる。

コンテナ名は `.env` で指定する。

イメージは、再現性のためバージョンを固定する。  
FreeRADIUS 4.x にはリリースの区切りがないため、開発ブランチからビルドしたイメージ（[freeradius-server-image](https://github.com/jolly-jive/freeradius-server-image)）を特定のビルドに固定して使う。固定は、それをもとに送信元の制限（「接続元の制限」）を加える `freeradius/build/Dockerfile` の `FROM` で行う。  
自前でビルドするイメージ（OpenLDAP、tftpd-hpa、OpenSSH）は、Alpine のリリース（3.24）に固定する。パッケージの版は、ビルドした時点のそのリリースのものになる。

OpenLDAP を自前でビルドするのは、既製のイメージに頼ると、その更新が止まったときに古い OpenLDAP を使い続けることになるためである（3.1 節）。Alpine のパッケージ（`openldap`、`openldap-back-mdb`、`memberof`・`refint`・`ppolicy` のオーバーレイ）に起動スクリプトを足しただけの構成で、ルートファイルシステムは読み取り専用にしている。`slapd` は syslog に出力させ、tftpd-hpa と同じく busybox の `syslogd` でコンテナの標準出力へ流す（`TZ` の時刻が付く）。ログのレベルは `compose.yaml` の `LDAP_LOG_LEVEL`（既定は `stats`）で、起動のたびに設定へ書き込む。

タイムゾーンは `.env` の `TZ` で指定し、全コンテナに環境変数として渡す。ログの時刻をコンテナ間で揃えるためである。

### ネットワーク

コンテナは Compose のデフォルトネットワーク（ブリッジ）1つに接続し、互いをコンテナ名で解決する。  
サブネットは `.env` の `DOCKER_SUBNET` で指定する。Docker に自動で割り当てさせると、管理対象のネットワークと重なる範囲が選ばれることがあるためである。  
コンテナごとの IP アドレスは固定しない。

利用者作業用コンテナは、このネットワークには接続せず、OpenLDAP とだけつながる専用のネットワーク（`openssh`）に置く（7.4 節）。サブネットは `.env` の `OPENSSH_SUBNET` で指定する。

ポートは IPv4 でのみ公開する（`compose.yaml` の `ports` に `0.0.0.0` を付ける）。  
アドレスを付けないと、Docker は IPv6 でも待ち受ける。どちらのネットワークも IPv6 を持たないので、IPv6 で届いた通信は Docker が中継し、コンテナからはブリッジのゲートウェイ（プライベートアドレス）から届いたように見える。これは FreeRADIUS の送信元の制限（5.1 節）を通ってしまう。  
IPv6 に対応するときは、ネットワークに IPv6 を持たせ、送信元の制限を IPv6 にも設けたうえで公開する。

### 接続元の制限

機器が使う3つのサービス（RADIUS、syslog、TFTP）は、機器のネットワークからの通信だけを受け付ける。  
ネットワークは `.env` の `DEVICE_NETWORKS` に、IPv4 のアドレスかプレフィックスを空白で区切って書く。既定はプライベートアドレスの全体（10/8、172.16/12、192.168/16）とし、利用者が管理用のネットワークに絞る。

利用者作業用コンテナ（SSH）は、接続元が機器ではなく人の端末なので、別の変数（`OPENSSH_ALLOWED_NETWORKS`）で指定する。書き方と既定は同じである。  
変数を分けるのは、絞るときのためである。1つにすると、片方を絞りたいときにもう片方の都合で広げることになる。分けておけば、機器の側は管理用のネットワークだけに、端末の側は執務室の LAN や VPN の範囲だけにできる。

変数は相手ごとに1つにして、制限の掛け方はサービスごとに分ける。

| サービス   | 方法                                               | 設定の渡し方                                                     |
| ---------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| FreeRADIUS | コンテナの中のパケットフィルタ（nftables）          | 環境変数。`entrypoint.sh` が起動の前にルールを入れる             |
| syslog-ng  | ログの経路に置くフィルタ（`netmask()`）             | 生成した `syslog-ng/config/device_networks.conf` を `@include` する |
| tftpd-hpa  | コンテナの中のパケットフィルタ（nftables）          | 環境変数。`entrypoint.sh` が起動の前にルールを入れる             |
| OpenSSH    | コンテナの中のパケットフィルタ（nftables）          | 環境変数。`entrypoint.sh` が起動の前にルールを入れる             |

- syslog-ng のファイルは `scripts/generate_device_networks.sh`（`make device_networks`）が書く。
- 本体に機能があるものは、それを使う。syslog-ng は外部のイメージであり、パケットフィルタを入れるには、派生したイメージをビルドして起動の処理を包むことになる。イメージを更新するたびに、その包みが働いているかを確かめる必要が生じる。
- FreeRADIUS も外部のイメージだが、本体の機能では制限できないので、派生したイメージ（`freeradius/build/`）をビルドしてパケットフィルタを使う。
  - v4 の待ち受けにも `networks`（`allow`）があるが、これは dynamic clients を定義してよい送信元の制限で、dynamic clients を使わないときは無視される。当初はこれで制限していたつもりだったが、効いていなかった（`clients.conf` に登録した機器なら、範囲の外からでも応答した）。
  - `recv Access-Request` のポリシーで送信元を見て応答しない方式も考えられる。採らなかったのは、パケットが `radiusd` に届き、クライアントの照合を済ませたあとの判定になるため、またほかのサービスと仕組みが揃わないためである。
  - tftpd-hpa と同じく、ルールを入れたあとで `NET_ADMIN` を落としてから、元のイメージの起動の処理に渡す。`radiusd` は root で起動してから降格する。
  - イメージを更新するときは、`FROM` のタグを変えてビルドし直し、スモークテストでフィルタが働いていることを確かめる。
- tftpd-hpa には機能がないので、パケットフィルタを使う。イメージは自前でビルドしているので、起動の処理に組み込める。
  - コンテナに `NET_ADMIN` のケーパビリティを与える。`entrypoint.sh` はルールを入れたあと、このケーパビリティを落としてから `in.tftpd` を起動する。`in.tftpd` の待ち受けのプロセスは root のまま残るので、落とさないとルールを書き換えられる。
  - 見るのは要求（69/udp）だけでよい。転送はサーバが別のポートから送り始めるので、確立済みの通信として通る。
  - ルールを入れられないとき（変数が空、書式の誤り、ケーパビリティがない）は起動しない。制限のないまま待ち受けることを避ける。
- OpenSSH も、パケットフィルタを使う（22/tcp）。sshd の設定でも接続元は絞れるが、接続を受けて認証の段階まで進んでから断ることになる。SSH でのパスワードの失敗はパスワードポリシーのロック（4.8 節）に数えられ、ロックされたユーザは機器にもログインできなくなるので、範囲の外からは認証まで進ませない。
  - tftpd-hpa と同じく、ルールを入れたあとで `NET_ADMIN` を落とす。sshd も `nslcd` も root で起動するので、`entrypoint.sh` が自分自身を起動し直して、以降のすべてのプロセスから落とす。
  - OpenLDAP からの応答は確立済みの通信として、Docker の内蔵 DNS への問い合わせはループバックの通信として通る。
  - 同じ表に、出ていく側のルールも入れる（`OPENSSH_EGRESS` の値ごとに違う。7.8 節、7.9 節）。こちらは接続元ではなく宛先の制限で、ほかのサービスにはない。
- FreeRADIUS は、このネットワークに加えてループバックを常に受け付ける。スモークテストがコンテナの中から要求を送るためである。
- 範囲の外から届いたものには、どのサービスも応答を返さない。

`clients.conf` に登録されたアドレスから範囲を導く方式は採らなかった。

- 機器は、RADIUS と TFTP で送信元のアドレスが違うことがある。
- TFTP は、ブートローダーからのファームウェアの取得のように、機器が RADIUS を使えるようになる前にも使われる。
- `clients.conf` は共有シークレットを含み、ホスト名でも書ける。ほかのサービスに渡す形に読み替えるのは壊れやすい。

Docker ホスト側のファイアウォールで一括して制限する方式も採らなかった。root 権限の手作業になり、スモークテストで確かめられないためである。

Docker ホスト自身から送ったものは、コンテナからはネットワークのゲートウェイから届いたように見える。ホストから動作を確かめるには、`DOCKER_SUBNET`（SSH は `OPENSSH_SUBNET`）が範囲に含まれている必要がある。

スモークテストは、Docker ホストからテスト用のスタックの syslog-ng と tftpd-hpa に送り、範囲に含まれるときは届き、範囲を変えて作り直すと届かないことを確かめる。FreeRADIUS も同じで、Docker ホストには `radclient` がないので、同じイメージの別のコンテナ（同じネットワーク）から送る。SSH も同じで、範囲を変えて作り直すと、sshd が待ち受けていても接続がタイムアウトすることを確かめる。

**課題**

- LDAPS（636/tcp）には制限を設けていない。クライアント証明書を要求しているので（4.5 節）、証明書のない相手は接続できない。

### 永続化対象

- LDAP データベースと LDAP の設定（`slapd.d`）
- FreeRADIUS のログ（コンテナの実行ユーザ uid 101 の所有とする）
- SYSLOG ログディレクトリ（NVMe）
- TFTP ディレクトリ（`/tftpboot`）
- TFTP の転送の記録（`tftpd-hpa/log/`）

FreeRADIUS の設定と証明書は永続化対象ではなく、ホスト側のファイルを読み取り専用でマウントする。

### バックアップと復元

`bin/backup.sh` が、作り直せないものを1つのアーカイブ（tar.gz、0600）にまとめ、`bin/restore_ldap.sh` がそのディレクトリを空の OpenLDAP に読み込む。手順は `docs/backup.md`。

**対象**

| 入れるもの | 理由 |
| --- | --- |
| `.env`、`clients.conf` | 利用者が書いたもので、生成できない |
| `secrets/` | ディレクトリが覚えているパスワードと一致している必要がある（4.10 節、4.11 節） |
| `openssh/hostkeys/` | 作り直すと全ユーザーの手元で警告が出る |
| ディレクトリ（`cn=config` とデータ） | ユーザー、ロール、パスワード、ロック、`nextUidNumber` |
| `tftpd-hpa/tftpboot/configs/` | 機器が送ってきたもので、ほかに写しがない |

入れないもの:

- ログ。冗長構成（2台）を前提とし、機器は両方のサーバへログを送るので、失ったサーバのログはもう片方に残る。
- `firmware/`。ベンダーから取り直せる。
- `make` が作り直すもの（`CA/`、LDIF、`ldap_openldap` など）。証明書はスタックのコンテナ間でしか使わないので、新しい CA で困らない。
- Docker ホストでの `sudo` の作業。手順をやり直し、`make host_check` で確かめる。

**方式**

- ディレクトリは、稼働中のコンテナで `slapcat -n 0` と `slapcat -n 1` を書き出す。`openldap/data/` を写すのではない。back-mdb は稼働中でも一貫した状態を読め、uid 100 の所有のファイルを読むための `sudo` も要らない。
- `configs/` は tftpd-hpa のコンテナの中で `tar` にする。ロール `admin` のユーザーが置いたファイルは、グループ 10001 にしか読めない場合があり、Docker ホストのユーザーからは読めない。コンテナの中なら所有者を数値のまま残せる。イメージファイルの `lost+found` は除く。
- `clients.conf` とホスト鍵は、コンテナのマウント元から取る。テスト用のスタックでも、そのスタックが使っているファイルを取れる。
- アーカイブにはディレクトリのエントリを入れない。リポジトリに展開したとき、既存のディレクトリのパーミッションを変えないため。
- 暗号化はしない（ユーザーの判断。置き場所とコピーの経路は、こいとはん管理者に任せ、注意を運用ガイドに書く）。
- `-k` で古いアーカイブを消す。消すのは新しいアーカイブを書き終えたあとだけで、失敗が続いても、古いものが消えていくことはない。定期実行は、こいとはん管理者の crontab の例を示すだけで、`make` には含めない。

**復元**

- 空の永続データにだけ読み込む。中身があれば断り、消すのはこいとはん管理者の作業とする（ディレクトリの中身が失われるため）。
- `cn=config` も、初期投入をやり直すのではなく、バックアップから戻す。手で変更した設定も含めて、バックアップの時点に揃えるため。初期投入の目印（4.6 節）を置き、起動スクリプトに投入をさせない。
- `slapadd` は、OpenLDAP のコンテナのボリュームを `--volumes-from` で借りた、同じイメージの別のコンテナで実行する。`sudo` が要らず、テスト用のスタックの匿名ボリュームにも届く。コンテナがなければ、起動せずに作る。
- 途中で失敗したときは、読み込んだものを消す（元は空なので、消してよい）。
- `secrets/` のサービスアカウントのパスワードがバックアップと違えば警告する。直すのは `bin/change_service_account_password.sh`。
- スモークテストが、バックアップ、OpenLDAP の作り直し、復元を通して確かめる（5.6 節）。

## 9. Raspberry Pi 5 リソース設計

- **CPU:** 全サービス軽量のため余裕あり。RADIUS / LDAP は CPU負荷ほぼゼロ、SYSLOG がログ量に応じて多少負荷。
- **メモリ:** 4GB で十分、8GB なら余裕。
- **ストレージ:** NVMe 256〜512GB を推奨（SYSLOG 3年保持を考慮）。

## 11. 未決定事項: DHCP と DNS

Kea DHCP と BIND9 を追加するかどうかは未決定である。

**論点:**

- DHCP と DNS を提供するには、ネットワーク機器の台帳（MAC アドレス、IP アドレス、ホスト名など）が必要になる。
- 台帳のために別のデータベースを配置するのは、本プロダクトの規模に対して重い。
- 既にある LDAP に機器情報を置けば、データベースを追加せずに済む。

**検討メモ:**

- 機器の IP アドレス、共有シークレット、機器種別は、既に `clients.conf` に書いている。LDAP に台帳を置く場合、`clients.conf` がその最初の利用者になる。
- Kea と BIND9 は LDAP を直接は参照できない見込みであり、LDAP から設定ファイルを生成して反映する仕組みが必要になる。これは `.env` から設定を生成する現在の方式の延長にあたる。
- ログローテーションは台帳に依存しないため、この判断を待たずに実装した（6.2 節）。

## 13. まとめ

本設計は、  
**「ネットワーク機器管理バックエンドを Raspberry Pi 5 上に構築する」**  
という目的に対して、機能・拡張性・保守性のバランスを取った構成である。

- OpenLDAP → 軽量でロール管理に適した ID 基盤。
- FreeRADIUS → 機器種別 × ロールによる柔軟な認可モデル。
- syslog-ng → 長期ログ保持とホスト別管理に強いログ基盤。
- tftpd-hpa → ファームウェア・コンフィグ配布に適した TFTP。
- OpenSSH → ログとファイルを扱うための、ユーザの作業環境。

認証・認可、ログ収集、TFTP、利用者作業用コンテナ（7 節）は実装済みである。ユーザ管理のスクリプト（4.7 節）、パスワードポリシー（4.8 節）、ログローテーション（6.2 節）も実装済みである。利用者作業用コンテナの公開鍵認証（7.6 節）は、要望が上がり、必要性を確かめるまで保留とする。DHCP と DNS は、機器台帳の持ち方とあわせて判断する。
