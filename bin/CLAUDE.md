# CLAUDE.md(`bin/`)

リポジトリの直下の `CLAUDE.md` の続きで、`bin/` に関わる部分。全体の構成、コマンド、複数のディレクトリにまたがる注意は直下にある。

**ユーザーの管理(`bin/manage_users.sh`)。** `scripts/` は構築のための生成スクリプト(`make` から呼ぶ)、`bin/` は稼働中のスタックに対する運用のスクリプト(こいとはん管理者が直接実行する)と、性格で分けている。Docker ホストで実行し、OpenLDAP のコンテナの `ldapi:///` と、OpenSSH のコンテナの `pwqcheck` と `koitohan-update-users` を `docker compose exec` で使う。`delete` と `role` のあとのセッションの切断は、`koitohan-update-users` が行う(スクリプトは自分で切らない。相手の台やスクリプトの外の変更でも同じに切れるよう、1か所にまとめた。`openssh/CLAUDE.md`)。対象のスタックは `COMPOSE_PROJECT_NAME` と `COMPOSE_FILE` で変えられ、指定しなければ稼働中のスタックを書き換える。試すときはテスト用のスタックに向けること(`KEEP=1 make test` で残せる)。パスワードは `ldappasswd -T /dev/stdin` で渡す。エントリに `userPassword` を平文で書かないこと(ppolicy を適用していないデータベースでは、ハッシュ化されずに保存される)。`uidNumber` は `cn=nextUidNumber,<サフィックス>`(`device` の `serialNumber`)から取り、再利用しない。このエントリは最初の `add` が作る。`unlock` は ppolicy のロックを解除する。設計は `docs/basic-design.md` の 4.7 節と 4.9 節。

**バックアップと復元(`bin/backup.sh`、`bin/restore_ldap.sh`)。** 手順は `docs/backup.md`。アーカイブに入れるのは `.env`、`clients.conf`、`secrets/`、`openssh/hostkeys/`、ディレクトリ(`ldap/config.ldif` と `ldap/data.ldif`。稼働中のコンテナで `slapcat -n 0` と `-n 1`)、`tftp-configs.tar`(tftpd-hpa のコンテナの中で `tar` にした `configs/`。`lost+found` を除く)、`koitohan-backup.txt`(日時、ホスト、コミット)。ログと `firmware/` は入れない(ログは冗長構成のもう片方に残り、ファームウェアは取り直せる、というユーザーの決定)。`make` が作り直すもの(`CA/` など)も入れない。暗号化しないのもユーザーの決定で、注意を運用ガイドに書いている。`configs/` をコンテナの中で取るのは、ロール `admin` のユーザーが置いたファイルが Docker ホストのユーザーから読めない場合があるため。`clients.conf` とホスト鍵はコンテナのマウント元から、`secrets/` は `KOITOHAN_GENERATED_ROOT` から取る(OpenLDAP がそこのファイルをマウントしているかを確かめる。外さないこと)。アーカイブはファイルだけを並べ、ディレクトリのエントリを入れない(リポジトリに展開したとき、既存のディレクトリのパーミッションを変えないため。`find -type f` と `--no-recursion` を外さないこと)。`-k` で古いものを消すのは、新しいものを書き終えたあとだけ(失敗が続いても古いものが消えていかないため)。定期実行は crontab の例を示すだけで、`make` には含めない。`restore_ldap.sh` は空の永続データにだけ読み込み、`cn=config` もバックアップから戻して(初期投入はやり直さない)、初期投入の目印を置く。中身があれば断る(消すのはこいとはん管理者の作業。ディレクトリの中身が失われる)。`slapadd` は、OpenLDAP のコンテナのボリュームを `--volumes-from` で借りた、同じイメージの別のコンテナで動かす(`sudo` が要らず、テスト用のスタックの匿名ボリュームにも届く。`docker compose run` だと匿名ボリュームが新しく作られる)。コンテナがなければ `docker compose create` で起動せずに作る。途中で失敗したら読み込んだものを消す。`secrets/` は戻さない(管理者のパスワードは起動のたびにファイルから書かれ、FreeRADIUS と OpenSSH は証明書で bind するので、ディレクトリと揃える必要がない)。以前の版のアーカイブには `ou=ServiceAccounts` が入っているが、そのまま戻る(アクセス制御は起動のたびに書き直されるので、読み取りの権限は持たない)。設計は `docs/basic-design.md` の 8 節の「バックアップと復元」。

**稼働の確認(`bin/check_services.sh`)。** 手順は `docs/monitoring.md`。止まっても気づかれにくいサービスを、cron から定期実行して確かめてもらうためのもの(Koitohan とは別の監視は期待できない、という前提。設計書の 8 節の「稼働の確認」)。確かめるだけで通知はせず、定期実行と送り先はこいとはん管理者に任せる(crontab の例を示すだけで、`make` には含めない)。`-q` で `OK` と `SKIP` を出さないので、cron の `MAILTO` で異常のときだけ届き、`-q` なしの毎日の実行が「I'm OK」になる。前回の結果は覚えない。出力の形は `check_host.sh` と同じ(`NG` があれば 1)。要求はどれもコンテナの中からループバックで送る(Docker ホストからだと送信元がゲートウェイになり、`DEVICE_NETWORKS` に断られうる)。OpenLDAP は OpenSSH のコンテナから、その証明書で LDAPS に bind し(SASL EXTERNAL)、サフィックスのエントリを読めることで見る(対応づけかアクセス制御が欠けると、bind はできても読めない)。FreeRADIUS は Status-Server だけで、確認用のユーザーは作らない(ロールを持たせないと bind まで届かず、持たせると機器に入れる資格情報になる。ppolicy のロックも絡む。ユーザーの決定)。そのため FreeRADIUS から LDAP への経路は確かめていない。共有シークレットは、FreeRADIUS のコンテナがマウントしている `clients.conf` から `127.0.0.1` を含む最初のクライアントのものを読み(なければ WARN で飛ばす)、標準入力からコンテナの中の一時ファイルへ渡して `radclient -S` で読ませる(引数に載せないこと。`ps` で見える)。tftpd-hpa は `firmware/` にないファイル(`koitohan-service-check`)を要求し、`File not found` が返ることで判定する(ファームウェアは大きいので取得しない。`tftp` はエラーでも 0 で終わり、応答がないと異常終了するので、メッセージで見る。実行のたびに `tftpd.log` に1行残る)。`configs/` はループバックイメージかどうかでなく、所有者が uid 1000 かで判定する(イメージを使わない環境で WARN が届き続けないため。マウントが外れると root 所有の下のディレクトリが見える)。chrony は `chronyc tracking` の `Leap status` で見る。空き(90%)と証明書の期限(30 日)は先頭の定数。
